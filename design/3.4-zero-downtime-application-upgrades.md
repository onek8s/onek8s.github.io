# 3.4 Zero-downtime application upgrades

**Requirements:** [R23](../requirements/0.2-requirements.md#r23), [R24](../requirements/0.2-requirements.md#r24), [R26](../requirements/0.2-requirements.md#r26).

The same rules apply in every cluster and are **enforced by admission policy** (Azure Policy add-on), so no
application can be deployed in a way that breaks a zero-downtime rollout or a node drain:

| Guardrail | Stateless | Stateful |
|---|---|---|
| Replicas | `replicas` / HPA `minReplicas` ≥ 2, or 0 (switched off; nothing in between) | ≥ 3, one per AZ |
| Spread | `topologySpreadConstraints` over nodes | `topologySpreadConstraints` over `topology.kubernetes.io/zone` |
| PodDisruptionBudget | Mandatory, `maxUnavailable ≥ 1` | Mandatory, `maxUnavailable: 1` |
| Rollout strategy | `RollingUpdate`, `maxUnavailable: 0`, any `maxSurge ≥ 1` | `RollingUpdate` (optionally `partition` for canary) or operator-managed |
| Probes | readiness + liveness (+ startup) required | readiness gated on replication / quorum |
| Graceful shutdown | `preStop` delay + `terminationGracePeriodSeconds` longer than the gateway's drain time | same, plus clean leader hand-over |
| Resources | requests required (HPA and the cluster autoscaler depend on them); resized in place by the VPA within Git bounds ([section 2.3](2.3-node-pools.md#pod-right-sizing-vertical-scaling-in-place)) | requests = limits for memory; VPA recommendations only |
| Images | From the environment's ACR only, by digest ([section 2.7](2.7-policy-enforcement.md)) | same |
| Non-serving workloads | See [below](#non-serving-workloads): the replica, spread, budget and rollout rows apply to serving workloads only | same |

- **Scaling on load** (stateless): HPA on CPU/memory (KEDA on queue length / request rate when a team needs it);
  the cluster autoscaler adds nodes for
  pods that do not fit and removes them again. `maxReplicas` and the zone pools' maximum are sized so that
  one cluster can take the full load. Vertically, the VPA resizes running pods **in place** – no new pod, usually no
  restart – within the bounds in Git ([pod right-sizing](2.3-node-pools.md#pod-right-sizing-vertical-scaling-in-place)),
  so following the load needs no release; only changing the bounds does.
- **No scaling on load in the stateful cluster**: replica counts and node pool sizes are fixed and changed as planned
  changes through the pipeline and IaC.
- **Compatibility rule**: during a release two versions run at the same time (for a few minutes inside the home cell
  during the rolling update, and in different cells for applications at home in different cells), so API and message changes must be backwards compatible and
  database changes follow *expand → migrate → contract* over separate releases. The single home cell reduces what
  *clients* see of this, but rollbacks and the data shared by all cells still meet both versions.

## Non-serving workloads

Jobs, scheduled jobs and queue consumers serve no request, so the rules above that keep a request flowing do not
apply to them ([R23](../requirements/0.2-requirements.md#r23), [R24](../requirements/0.2-requirements.md#r24)); what
applies is that their work completes exactly as often as intended while cells are drained and released:

| Workload | Runs as | The rules |
|---|---|---|
| A finite job | `Job` with `backoffLimit`, `activeDeadlineSeconds` and `ttlSecondsAfterFinished`, judged by its exit status | Idempotent, so a restart after a drain repeats nothing twice; resource requests; the same image, security and placement rules as a pod of the application |
| A scheduled job | `CronJob` with `concurrencyPolicy: Forbid` and a `startingDeadlineSeconds` | Runs in the application's **home cell** - in both exposures, an external application's non-serving workloads are placed in one cell like an internal application and migrated the same way ([internal zones](3.1-cluster-types-stateless-and-stateful.md#one-home-cell-per-application-moved-by-migration)) - so a schedule fires once per environment, never once per cell |
| A queue consumer | `Deployment` with at least 1 replica, scaled on queue length (KEDA), readiness and liveness probes, a graceful shutdown longer than its longest message, `RollingUpdate` | May run in every cell, because the queue serialises the work; below 2 replicas it needs no disruption budget and a drain costs it a pause, not data |

**During a cell drain** a running job is given the drain timeout to finish; a job still running then is stopped and
restarted in the target cell by its `CronJob` or owner, which is why it must be idempotent. A release moves a
non-serving workload with the cell's branch like any other manifest; the SLO gates do not see it, so a team sets an
alert on its own measure of success (last run, queue lag) in its observability directory.

## Releases cell by cell

A release – a signed commit of `main` with any number of application changes ([section 3.3](3.3-keeping-clusters-in-sync.md)) – moves through the
cells of an environment **one cell at a time**, with the same *drain → change → test → return* procedure as a
cluster upgrade ([section 3.5](3.5-zero-downtime-cluster-upgrades.md#stateless-clusters)), except that nothing is migrated out:
every application, internal or external, runs only in its home cell
([incoming traffic](3.1-cluster-types-stateless-and-stateful.md#incoming-traffic-from-outside-and-from-inside)), so
every interactive user switches from the old to the new version **exactly once and never back**:

1. **Stateful stage first** (only if the environment has a stateful cluster): providers before consumers
   ([section 3.3](3.3-keeping-clusters-in-sync.md)).
2. **Deploy to cell 1**: the pipeline moves the cell's branch (`<env>-sl-az1`) to the commit; Flux rolls it out and
   the pipeline waits until all Kustomizations are `Ready`. The applications whose home is cell 1 are updated **in
   place** by their zero-downtime rolling update – this is the moment their users switch to the new version.
3. **Test** through the per-cell test host names: smoke and synthetic tests over the real TLS path. The pipeline
   watches the error-rate and latency SLOs per cell in Grafana Cloud ([SLO gates](6.2-observability-with-grafana-cloud.md#what-grafana-cloud-does));
   on a breach it moves the branch back, which rolls back the cell's applications.
4. **Soak**, then repeat for the next cell. After the last cell all clients are on the new version.

A client always uses its application's home cell, so it switches from the old to the new version **once and never
back**:

| Client | What it sees during a release |
|---|---|
| Any client (Internet, corporate network, other Azure workloads) | One version at a time, except during the few minutes of the rolling update in the home cell; switches once, old → new |
| Long-lived connection (WebSocket, SSE) | Reconnects when its pod is replaced, then follows the rule above |

Consequences:

- **Releases are trains.** Each cell costs one rollout, its tests and a soak, so many changes
  ride in one release instead of one release per application change. An urgent fix takes the same path with
  a shorter soak.
- **The first cell is the canary**: the first cell that is home to some applications, so placing a few low-risk
  applications in every cell makes sense.
  In-cell progressive delivery (Flagger with `HTTPRoute` weights on the zone's gateway) is not used for
  interactive applications: it splits requests inside the cell, so their clients would jump between versions again. It stays an option for back-end APIs that are strictly backwards compatible.
