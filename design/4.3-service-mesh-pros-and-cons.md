# 4.3 Service mesh: pros and cons

**Requirements:** [R2](../requirements/0.2-requirements.md#r2), [R12](../requirements/0.2-requirements.md#r12), [R15](../requirements/0.2-requirements.md#r15), [R22](../requirements/0.2-requirements.md#r22).

The stateless clusters run **no service mesh** ([R22](../requirements/0.2-requirements.md#r22)); the stateful cluster
leaves TLS to its applications ([R21](../requirements/0.2-requirements.md#r21)). The question comes back with every
new Istio or AKS feature, so this page keeps the reasoning: what a mesh would give, what it would cost, and - the
deciding question - whether it would keep the isolation zones apart
([R2](../requirements/0.2-requirements.md#r2), [section 2.4](2.4-allowed-and-blocked-flows.md#isolation-matrix)).
Adding one needs a change of R22 first, which is a human's.

## What a mesh gives, and what the platform does instead

| A mesh gives | The platform does instead | What is missing without the mesh |
|---|---|---|
| **Encryption between services** (mTLS) | Azure Virtual Network encryption between nodes; traffic between pods of one node never leaves the host | Nothing in transit: every hop is encrypted either way. What mTLS adds is a workload *identity* on the wire, which the next row covers. Since Kubernetes 1.37 the building blocks for that identity are in-core and GA - `PodCertificateRequest` (the kubelet obtains an X.509 certificate per pod from a signer) and `ClusterTrustBundle` (the CA bundle every pod can mount) - but AKS ships no signer, so using them means running one |
| **Identity-based authorisation** (which service may call which) | Cilium policies by namespace and label decide which pods may connect; applications validate Entra ID tokens of their callers for *who* may call *what* | Authorisation by network identity without code in the application. Here it lives in the application, which already has to validate the caller's token for its own data |
| **Layer 7 traffic management**: retries, timeouts, circuit breaking, traffic shifting, fault injection | Releases move cell by cell behind the cell router ([section 3.4](3.4-zero-downtime-application-upgrades.md#releases-cell-by-cell)); retries and timeouts are the client library's | In-cell canaries by request share - deliberately not used for interactive applications |
| **Telemetry without code**: per-request metrics and traces between services | The zone's gateway gives the first span and the default SLOs; Beyla's eBPF instrumentation in Grafana Alloy gives per-service RED metrics without code ([section 6.2](6.2-observability-with-grafana-cloud.md)); applications emit OpenTelemetry | Nothing of substance since Beyla |
| **Egress control by name** | The hub Firewall per zone, from per-application rule files ([section 5.1](5.1-egress-control-and-the-company-firewall.md)) | – |

## Pros and cons

| Pros of a mesh | Cons of a mesh |
|---|---|
| A workload identity on the wire (mTLS), checked on every connection, without code in the application | A data plane in every pod's path - sidecars, or ambient's per-node ztunnel and per-namespace waypoints - that the platform runs, upgrades and debugs; a broken proxy breaks the application |
| Authorisation by service and by HTTP method and path between services, written by the platform rather than in each application | A second policy language next to Cilium policies and `HTTPRoute`s, and a second place where a flow can be refused |
| Retries, timeouts, circuit breaking and traffic shifting as configuration | The largest cloud-specific component in the cluster, against the portable application contract ([section 1.3](1.3-open-standards-and-portability.md)) |
| Per-request metrics and traces between services without code (mostly covered by Beyla already) | Every hop inside a zone is already encrypted (VNet encryption between nodes, the host within a node): mTLS adds identity, not secrecy |
| A recognised answer when a regulation or a customer asks for authentication between workloads | A control plane on the system pool that every application pod depends on, with its CPU and memory, in a cell whose system pool is sized small |
| | AKS's managed Istio cannot run next to App Routing's istiod, the second Gateway API implementation ([section 4.1](4.1-encryption-in-transit-and-tls.md)) |

## A mesh and the isolation zones

Inside a zone a mesh works as anywhere else. The question is what sits above the zones: the control plane, which
reads every namespace it serves and hands out the configuration, and the certificate authority, which every
identity in the mesh is signed by.

| Option | Control plane and CA | Zone isolation |
|---|---|---|
| **AKS's managed Istio add-on** (sidecars) | One istiod and one root CA per cluster; revisions exist for upgrades, not for tenants | **Per cell, not per zone.** Every zone shares one control plane, which reads every zone's `Service`s, endpoints and `Secret`s, and one trust domain: an identity (`<trust domain>/ns/<namespace>/sa/<service account>`) names the namespace, not the zone. The zones still cannot reach each other - Cilium, the NSGs and the hub Firewall keep refusing it - but if istiod fails, every zone's mesh is affected: the cell is the bulkhead, the same weakness as App Routing's istiod ([section 4.1](4.1-encryption-in-transit-and-tls.md)). Cannot run next to App Routing |
| **AKS's managed ambient Istio** (Application Network, preview) | Managed per cluster, enrolled per namespace | As the add-on: one control plane and one CA per cell. ztunnel runs on every node; since a zone's nodes carry only that zone's pods, a ztunnel holds only one zone's identities |
| **Self-managed Istio, one control plane per zone** | An istiod per zone in a platform namespace, limited to the zone's namespaces (`discoverySelectors` on `platform/zone=<zone>`), its own CA and trust domain; sidecars injected by the zone's revision | **Per zone.** A zone's istiod reads only its zone, signs only its zone's identities, and its failure stays in the zone. Left shared: Istio's CRDs and admission webhooks, which are cluster-wide. The platform runs and upgrades the control planes itself, not AKS, and ambient's per-node ztunnel does not fit several control planes in one cluster: sidecars only |

Between zones a mesh would add little: a zone reaches another only as a client of its gateway's published name,
through the hub Firewall ([section 2.4](2.4-allowed-and-blocked-flows.md)), so mTLS could not span zones without
opening the paths the zones are built to close. A mesh would protect the traffic inside a zone, between its
applications.

## What adding a mesh would change

Whichever option, the platform would have to change before the first sidecar ran:

- **R22**: the requirement itself, a human's change.
- **Allowed images**: the proxy image would have to be mirrored into the environment's ACR and signed, or the
  sidecars are refused at admission (images by digest from the ACR only, [section 2.7](2.7-policy-enforcement.md)).
- **Flows between the pools**: sidecars on zone nodes reach the control plane on the system pool (xDS on TCP 15012,
  the injection webhook on 15017); that flow passes the hub Firewall
  ([section 2.1](2.1-network-layout.md)) and the zone's Cilium baseline, and both refuse it today. It would be one more
  row in [section 2.4](2.4-allowed-and-blocked-flows.md).
- **The gateways**: Traefik is not in the mesh; it would need a sidecar of the zone's control plane, or the zone's
  applications would accept plain h2c from the gateway beside mTLS from each other.
- **The system pool**: one control plane per zone means one per zone per cell, sized into the system pool.
- **One policy engine** ([R15](../requirements/0.2-requirements.md#r15)): the mesh's authorisation policies would be
  admitted, and constrained, by Azure Policy like every other object.

If a mesh is ever required, the way in is **one self-managed control plane per zone**, sidecars only, so that the
zone stays the bulkhead; AKS's managed mesh only once it can be scoped to a zone.
