# 3.6 Node pool upgrades: rolling or blue/green

**Requirements:** [R23](../requirements/0.2-requirements.md#r23), [R26](../requirements/0.2-requirements.md#r26), [R27](../requirements/0.2-requirements.md#r27).

A node pool's nodes are replaced whenever its Kubernetes version, its node image or a setting that only a new node
can take changes. AKS replaces them in place with a **rolling surge upgrade**; the platform can also replace a whole
pool with a **new generation beside it** - blue/green node pools. Both are offered from the first cell on, and the
version pipeline ([section 3.5](3.5-zero-downtime-cluster-upgrades.md)) chooses per change. This page weighs them.

AKS has no mode that leaves the old nodes in place, cordoned, and lets the cluster autoscaler bring the new version:
the autoscaler always adds nodes of the pool's current version, so the new version comes either from an upgrade of
the pool or from a new pool. That new pool is what blue/green means here.

## The options

| | Rolling surge upgrade (AKS) | Blue/green node pools (platform IaC) | Blue-green upgrade strategy (AKS, preview) |
|---|---|---|---|
| **How** | The pool's version changes; AKS adds surge nodes, then cordons, drains and replaces the old nodes a few at a time ([max surge, drain timeout, node soak](https://learn.microsoft.com/en-us/azure/aks/upgrade-aks-node-pools-rolling)) | A second **generation** of the zone's pools is added at the new version and settings; the old generation is **retired** (tainted, no new pods) and later **removed** - each step a pull request ([below](#bluegreen-node-pools)) | The pool's version changes with `upgradeStrategy: BlueGreen`; AKS creates the whole green node set, cordons every blue node, drains them in batches with a soak time per batch and a final soak, then deletes them ([AKS documentation](https://learn.microsoft.com/en-us/azure/aks/blue-green-node-pool-upgrade)) |
| **Which changes** | Kubernetes version, node image | Anything: also VM size, max pods, OS disk, OS SKU, subnet - what a running pool cannot change | Kubernetes version, node image |
| **When pods move** | When AKS drains their node, on AKS's schedule within the drain timeout | When the application next rolls out, restarts or scales out; what is left, when the old generation is removed - on the platform's schedule, as late as the application teams need | When AKS drains their batch |
| **Way back** | [Node pool rollback](https://learn.microsoft.com/en-us/azure/aks/roll-back-node-pool-version), itself another rolling replacement | Untaint the old generation and retire the new one, as long as the old one exists - no node is replaced | `az aks nodepool rollback`, during the final soak only |
| **Extra capacity** | The surge nodes (max surge per pool) | The new generation's nodes while both run - as many as the pods that have moved | The whole pool twice over |
| **Status** | GA | Plain AKS: node pools, taints, labels - nothing in preview | Preview |

## Pros and cons

**Rolling surge upgrade**

| Pros | Cons |
|---|---|
| One change, one pull request; AKS does the cordon, drain and replacement | Every pod of the pool is evicted on AKS's schedule, one surge batch at a time; a PDB that never allows an eviction blocks the upgrade until the drain timeout |
| Little extra capacity: the surge nodes | A bad version is found only after nodes have been replaced, and the way back is another full replacement |
| No change to pool names or IaC between upgrades | Only version and node image: a VM size, max pods or OS disk change still needs a new pool |

**Blue/green node pools**

| Pros | Cons |
|---|---|
| No forced eviction while both generations run: pods move at their own next rollout, so an application with long-lived connections or a slow start chooses when | Three pull requests and applies per pool change instead of one, and the version pipeline has to follow the steps |
| The way back is instant until the old generation is removed: untaint it, retire the new one | Two generations side by side need quota and node subnet addresses for both while they overlap |
| One procedure for every change, including those AKS cannot make on a running pool | Every pool name carries its generation (`se1spot`, `se2spot`), so tooling must never select a pool by name - the platform selects `platform/zone` only |
| Each zone moves on its own schedule; one zone's new generation is tested while the others stay | A generation left retiring holds old nodes, and their cost, until it is removed: the capacity agent reports it |
| Works the same in the stateful cluster, one zone and AZ at a time, without a drain to a surge node | |

**Blue-green upgrade strategy (AKS)**

| Pros | Cons |
|---|---|
| Blue/green behaviour without pool generations in IaC, the pool keeps its name | Preview: not used in acc and prd until it is GA |
| Batched drains with soak times and a rollback during the final soak | Every pod is still evicted on AKS's schedule, and the rollback window closes with the final soak |
| | Twice the pool's capacity during the upgrade, and version changes only |

## What the platform uses

- **Stateless cells: rolling surge by default.** The cell is out of traffic while it is upgraded
  ([section 3.5](3.5-zero-downtime-cluster-upgrades.md#stateless-clusters)), so an eviction costs no user request, and
  a regression is caught by the slow cells and the version pipeline's steps, not by the pool.
- **Blue/green pools in a stateless cell** for a change a running pool cannot take (VM size, max pods, OS disk,
  OS SKU), for a minor upgrade the version pipeline flags as risky, and for an application whose pods must not be
  evicted on AKS's schedule - they move at their next release, by a deadline the platform sets.
- **Stateful cluster: rolling surge, one AZ at a time; blue/green pools for a risky LTS minor jump**, zone by zone and
  AZ by AZ, where a way back that replaces no node is worth most
  ([section 3.5](3.5-zero-downtime-cluster-upgrades.md#stateful-cluster)).
- **AKS's blue-green strategy** once it is GA, in place of a rolling upgrade where the batched drain and the final
  soak help; it does not replace the platform's generations, which cover every change and leave the timing to the
  application.

## Blue/green node pools

Every zone pool belongs to a generation, a letter or digit in its name: `<country><generation>` and its `spot`,
`arm` and `armspot` pools in a stateless cell (`se1`, `se1spot`, `se1arm`, `se1armspot` - AKS allows 12 characters,
and the exposure is the cluster's own), `<country><generation>z<AZ>` in the stateful cluster (`fi1z1`). Every node
carries `platform/zone` and `platform/node-generation`; placement selects `platform/zone` only
([section 2.3](2.3-node-pools.md)), so pods land on any generation of their zone that takes them. A zone moves from
generation 1 to 2 in four steps, each a pull request to the cluster IaC:

1. **Pin** generation 1 to its version, then move the cluster's version: the control plane is upgraded, the pools
   of generation 1 are not (the Kubernetes version skew allows nodes up to three minors behind).
2. **Add** generation 2 in the zone: its pools are created empty, at the cluster's version and the newest node image,
   from zero nodes like every zone pool.
3. **Retire** generation 1 in the zone: its pools are tainted `platform/retiring=true:NoSchedule`. Running pods stay;
   every new pod - a rollout, a restart, a scale-out, a spot eviction - lands on generation 2, whose nodes the
   cluster autoscaler adds, and the autoscaler removes generation 1's nodes as they empty. The way back is to untaint
   generation 1 and retire generation 2.
4. **Remove** generation 1 from the zone once it is empty or its deadline has passed: AKS deletes its pools and drains
   what is left, PodDisruptionBudgets respected.

The quota, the node subnet and the zone pools' maximum must hold both generations while they overlap - the same
N+1 headroom a cell upgrade needs ([section 3.2](3.2-environments.md)). The plan warns when a zone would be left without a
generation that takes pods.
