# 7.4 Outlook: the platform in 2030, and the options kept open

This platform grows slowly, becomes the company's most important one around 2030 and must still be right in 2050,
decades after large-scale use began; 2030 is the first checkpoint on that road, not its end. Kubernetes ships three
minors a year, so the clusters of 2030 will run a version twelve minors away from today's 1.36, with APIs removed along the way; Azure will have renamed,
retired and replaced services; the workloads will include things nobody onboarded in 2026. This page answers the
question *what should an AKS platform look like in 2030 and beyond* the only way it can be answered honestly: by
naming the few bets that are meant to hold, the changes that are visible already, the rule that keeps the platform
simple while they arrive, and the list of features deliberately left out today together with the way to add each
one later. Dates and product states are as of October 2026.

## What is meant to hold

These are the bets. Each is cheap to keep and expensive to change, which is why the design spends its complexity
budget on them and nowhere else.

| Bet | Why it holds | Where it lives |
|---|---|---|
| **The application contract is open standards only**: Kubernetes GA APIs, OCI images, the Gateway API, External Secrets, OIDC workload identity, OpenTelemetry, PaaS over open protocols | Every cloud and every year of Kubernetes keeps them; an application written to them in 2026 deploys unchanged in 2030 | [Section 1.3](1.3-open-standards-and-portability.md) |
| **Clusters are cattle, cells are the unit of change** | A cell is drained, rebuilt and returned behind the cell router, so any cluster-level change - a Kubernetes minor, a CNI, a node OS, a feature that can only be set at creation - is a rebuild, not a migration | [Section 3.5](3.5-zero-downtime-cluster-upgrades.md), [D08](7.2-decisions.md#decision-matrix) |
| **Isolation zones are the blast-radius unit inside a cell**, with their own nodes, network, vault and policies | Countries, business units or regulated workloads map onto zones without a new cluster; a zone can become its own set of cells later ([cells and bulkheads](1.2-requirements.md#cells-and-bulkheads)) | [Section 1.2](1.2-requirements.md) |
| **Git is the only write path**, for humans and agents alike, behind a deterministic merge gate | The gate is where new automation is admitted and old automation is retired; the runtime guardrails do not depend on who or what wrote the change | [Section 6.1](6.1-ai-driven-day-2-operations.md) |
| **Data lives in managed services**; the stateful cluster is the last option and does not exist until needed | Databases, brokers and caches are where clouds compete on operations; the platform should not | [Section 3.1](3.1-cluster-types-stateless-and-stateful.md#where-does-a-workload-run) |
| **Private by default**: no public endpoint but the external zones' gateways and the firewall's own address | Every retirement of a public endpoint since 2024 moved in this direction; nothing moves back | [D60](7.2-decisions.md#decision-matrix) |
| **The platform operates itself through agents**, inside guardrails humans own | The ratio of clusters to engineers only grows; what changes is how much the gate trusts an agent, measured per agent and environment ([D25](7.2-decisions.md#decision-matrix)) | [Section 6.1](6.1-ai-driven-day-2-operations.md) |

## Keep it simple: the rule for adding a feature

Every row above tempts the platform to add something now "to be ready". The platform stays simple by refusing that
and keeping the *way in* ready instead ([decision D64](7.2-decisions.md#decision-matrix)). A feature is added only when
all of these hold:

1. **Something names it**: a requirement, a measurement in acceptance or production, or a sign-off - never a
   roadmap.
2. **The cloud manages it**: AKS installs, upgrades and supports it, or it is an open-source project the platform
   already runs. The platform runs no second control plane of its own.
3. **It is a per-cell switch**: it can be enabled on one cell, rolled out cell by cell behind the router and rolled
   back the same way. A rebuild counts as a switch; a migration does not.
4. **Applications do not notice**: nothing changes in a team's manifests, routes or secrets, or the platform
   generates what the feature needs from what the team already declared.
5. **The way out is written before the way in**: the decision records how to remove it again.

A feature that fails one of these is not added; it goes into the table below with the trigger that would make it
pass. The same five tests apply to removing something: a feature nothing names any more leaves the same way.

## The options kept open

What the platform deliberately does not do today, why, what would change that, and what adopting it later costs.
Every row is a per-cell or per-zone change; none of them changes the application contract.

## The roadmap watch list

There is no readable AKS roadmap: `aka.ms/aks/roadmap` points at a project board that needs a signed-in browser, and
Kubernetes publishes only the next minor's enhancement milestone. Following the roadmap therefore means reading each
AKS release note and each Kubernetes minor against this list - the upgrade agent does it per minor as part of the
version pipeline ([D68](7.2-decisions.md#decision-matrix), [section 6.1](6.1-ai-driven-day-2-operations.md#agents)), a person once a
year after Ignite. Proposals that have no release yet - open enhancement pull requests, working-group use cases,
mailing-list threads - are not in any release note: a person reads the working groups (node lifecycle, device
management, node identity, SIG Network's policy API, SIG Storage's data protection) once a quarter for the rows marked
*proposal*. Every row names the signal to look for and what in this design it closes; a row whose signal has
arrived becomes a decision, never a silent change. The list is written for the platform the company runs on from 2030 on,
growing slowly until then: the first rows are the previews the trust path already stands on, which must be GA or
replaced before that - a platform that important does not stand on previews.

## What this does not promise

The design does not predict which of these triggers fires. It promises that when one does, the answer is a decision
in [the log](7.2-decisions.md), a per-cell change rolled out the way every change is rolled out, and no change to
the applications. If by 2030 a feature on this list has become the obvious default for every cell, it joins the
cell module like NAP and Azure Linux did; if it has not, it stays an option. Either way the platform of 2030 is
recognisable from this page, and the one of 2050 is reached by the same rule applied twenty more times: nothing on this
page is meant to outlive its trigger, only the way of deciding is.
