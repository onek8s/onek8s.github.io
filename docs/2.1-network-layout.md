# 2.1 Network layout

![Network subnets](../images/2.1-network-subnets.svg)

Every cell has its own VNet with **one address space for nodes and load balancers**, cut into sixteen equal **slots**:
slot 0 is the system subnet (`snet-system`: the system pool, every zone's gateway pods and the API server's private
endpoint), slots 1 to 14 belong to the **isolation zones by their index**, which is the same in every cell of the
exposure, and slot 15 is reserved for the delegated API server subnet of VNet integration (H14). Inside a zone's slot
the first half is the zone's node subnet `snet-<zone>-nodes` and the fifth eighth its load balancer subnet
`snet-<zone>-ilb`; the rest is reserve. A **second address space holds the pods**: a `/16` of `100.64.0.0/10` with a
`/20` per slot index, `snet-system-pods` for the system pool's pods and `snet-<zone>-pods` per zone - about 4,000 pods
per zone, handed to the nodes in batches of sixteen ([D74](7.2-decisions.md#decision-matrix); the lab's values are in
the [address plan](3.1-cluster-types-stateless-and-stateful.md#vnets-and-address-plan)). A new zone takes a free slot
in every cell, so nothing existing is re-addressed. Private endpoints are not in the cells at all: they sit in one
shared subnet of the environment's network and are reached through the hub firewall.

| | Stateless cell | Stateful cluster (designed) |
|---|---|---|
| CNI | Azure CNI Pod Subnet with dynamic IP allocation, powered by Cilium ([D74](7.2-decisions.md#decision-matrix)); classic node pools with the cluster autoscaler ([section 2.3](2.3-node-pools.md)) | The same CNI |
| [ACNS](5.1-advanced-networking-and-fqdn-egress.md) | Off by default ([D61](7.2-decisions.md#decision-matrix)); on per cell where a zone needs per-application egress ([section 5.2](5.2-egress-control-options-and-the-company-firewall.md#acns-and-ebpf-host-routing-in-detail)) | FQDN egress policies + observability + eBPF host routing |
| Pod IPs | From the zone's `snet-<zone>-pods` - routable in the VNet, kept up to the hub firewall (AKS's masquerading agent translates nothing); the firewall SNATs them with the other private ranges | From `snet-<zone>-pods` - routable in the VNet |
| Which application may leave the cluster | The hub Firewall decides per zone from per-application rule files; its log names the pod; per application only with ACNS ([section 5.2](5.2-egress-control-options-and-the-company-firewall.md)) | Cilium FQDN policy per application ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md)) |
| `snet-<zone>-ilb` | Internal load balancer of the zone's gateway (internal zones; an external zone's gateway has a public load balancer, [section 3.1](3.1-cluster-types-stateless-and-stateful.md#external-zones-active-active-with-dns-affinity)) | Internal load balancers of the applications' `LoadBalancer` Services |
| Traffic to another zone of the same cell ([D73](7.2-decisions.md#decision-matrix)) | Everything meets the hub Firewall: pods, nodes and load balancers are in the zone's slots, and the zone's route table sits on its node and pod subnets | Same |

Zone isolation rests on every zone having its own nodes in its own subnets: a packet from a zone that leaves the
cluster always carries an address of that zone's slots. Every subnet has its own **NSG** (`nsg-<cell>-<subnet>`,
deny-all inbound as the last rule) and every node and pod subnet a **route table** with BGP propagation off. The system
subnets keep the cell's table (`rt-<cell>`), with `0.0.0.0/0` to the exposure's hub Firewall
([decision D53](7.2-decisions.md#decision-matrix)) as its only route. Each zone's node and pod subnets have the zone's
own table (`rt-<cell>-<zone>`): the same default route **plus a route per other zone's slot** - every node and pod slot
1 to 14 but the zone's own, occupied or free, so a new zone changes no table - to the same Firewall
([decision D73](7.2-decisions.md#decision-matrix)). The default route alone would not do that: a packet to another slot
of the cell matches the VNet's own system route, which is more specific than `0.0.0.0/0`, and would be delivered inside
the VNet without any firewall seeing it. A slot's route is more specific than the VNet's, so what one zone sends to
another zone leaves for the Firewall, which denies and logs it - nothing is allowed between zones
([R5](1.2-requirements.md), [section 2.4](2.4-allowed-and-blocked-flows.md)). Three prefixes stay on the VNet's route
on purpose: the zone's **own slots** (Azure applies a route to the traffic within a subnet as well, and the nodes of one
zone talk to each other directly), **slot 0**, the system subnets (the kubelet tunnel, metrics-server and the API
server's private endpoint are the platform's flows ① to ④, and every zone's gateway pods run there), and slot 15. So
inside a cell three layers separate the zones, in the order a packet meets them: the Firewall (L3-L7, logged), the
destination subnet's NSG and Cilium - and the Firewall is also the layer for everything that leaves the cell. A
zone-to-zone allow is a change to R5, not a Firewall rule: a flow the Firewall allowed would be hairpinned back into
the cell through the hub's peering, and one to another zone's gateway is answered from the system subnet, whose table
routes no slot to the Firewall, so it would also need the slots' routes on the system subnet's table.

What the NSGs allow on a node subnet, and from where:

- the kubelet port (TCP 10250) from the cell's system subnet (the AKS tunnel); Cilium health (TCP 4240), ICMP and
  DNS (53) between the cell's node subnets; the cell's pod subnets between the node subnets; load balancer probes from `AzureLoadBalancer`; ICMP from the hub
  firewall's address; traffic within the subnet. A pod subnet gets the rules of its pool's node subnet;
- TCP 443 from the **Internet** on the system subnet (every zone's gateway pods run there) and on an external
  zone's node subnet; TCP 443 from **`VirtualNetwork`** on an internal zone's node and load balancer subnets and on
  the system subnet - an NSG rule takes one service tag, and the corporate ranges arrive through the hub as
  `VirtualNetwork`.

> **Why subnets and not separate VNets?** AKS requires all node pool subnets and the API server subnet of one
> cluster to be in the same VNet. Within one cluster, "network per country" is therefore implemented as
> *a subnet slot per zone + NSG + Cilium, with the hub firewall between the slots ([D73](7.2-decisions.md#decision-matrix)) and for
> everything that leaves the cell*, which the security team accepts for countries. Internal and external are not separated this way: they are separate
> clusters in separate subscriptions behind separate hubs ([decisions D52, D53](7.2-decisions.md#decision-matrix)),
> so the picture shows an internal cell; an external cell's VNet (`vnet-prd-ext-stateless-az1`) is the same with
> `ext-fi` and `ext-se` in its slots.
> Should a hard VNet boundary per country ever be required, the same step is taken once more – **one cluster per
> zone** – and the address plan stays the same.
