# 2.1 Network layout

![Network subnets](../images/2.1-network-subnets.svg)

Every cell has its own VNet with **one address space**, cut into sixteen equal **slots**: slot 0 is the system
subnet (`snet-system`: the system pool, every zone's gateway pods and the API server's private endpoint), slots 1 to
14 belong to the **isolation zones by their index**, which is the same in every cell of the exposure, and slot 15 is
reserved for the delegated API server subnet of VNet integration (H14). Inside a zone's slot the first half is the
zone's node subnet `snet-<zone>-nodes` and the fifth eighth its load balancer subnet `snet-<zone>-ilb`; the rest is
reserve - in a pod-subnet cell the first half is the pod subnet `snet-<zone>-pods` and the nodes take the sixth
eighth ([address plan](3.1-cluster-types-stateless-and-stateful.md#vnets-and-address-plan)). A new zone takes a free
slot in every cell, so nothing existing is re-addressed. Private endpoints are not in the cells at all: they sit in
one shared subnet of the environment's network and are reached through the hub firewall. Whether the zone's pods
have VNet addresses depends on the cell's CNI mode:

| | Stateful cluster (designed) | Stateless cell, overlay (**deprecated**, [D76](7.2-decisions.md#decision-matrix); the lab's az2 keeps it for the tests and the security discussion) | Stateless cell, pod subnet (**the default**, [D76](7.2-decisions.md#decision-matrix), [D74](7.2-decisions.md#decision-matrix); the lab's az3 runs the legacy node subnet until it is rebuilt) |
|---|---|---|---|
| CNI | Azure CNI, VNet-integrated with dynamic pod IP allocation, powered by Cilium | Azure CNI Overlay, powered by Cilium | Azure CNI Pod Subnet with dynamic IP allocation, powered by Cilium - the same CNI as the stateful cluster; node auto provisioning does not support it yet, so such a cell runs classic node pools with the cluster autoscaler until it does ([section 2.3](2.3-node-pools.md#pod-subnet-cells-classic-node-pools-until-nap-supports-the-pod-subnet)) |
| [ACNS](5.1-advanced-networking-and-fqdn-egress.md) | FQDN egress policies + observability + eBPF host routing | Off by default ([D61](7.2-decisions.md#decision-matrix)); on per cell where a zone needs it ([section 5.2](5.2-egress-control-options-and-the-company-firewall.md#acns-and-ebpf-host-routing-in-detail)) | Same |
| Pod IPs | From `snet-<zone>-pods` – routable in the VNet | From the overlay range `100.201.0.0/16`, the same in every cell, outside the VNets | From the zone's `snet-<zone>-pods` in the zone's slot, in a `/16` of `100.64.0.0/10` per cell ([D59](7.2-decisions.md#decision-matrix), [D74](7.2-decisions.md#decision-matrix)) |
| Pod traffic leaving the cluster | Keeps the pod IP | SNAT to the node IP, so NSGs and the firewall see the zone's `snet-<zone>-nodes` | Keeps the pod IP up to the hub firewall (AKS's masquerading agent translates nothing); the firewall SNATs it with the other private ranges |
| Which application may leave the cluster | Cilium FQDN policy per application ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md)) | The hub Firewall decides per zone from per-application rule files; per application only with ACNS ([section 5.2](5.2-egress-control-options-and-the-company-firewall.md)) | The hub Firewall decides per zone; its log names the pod |
| `snet-<zone>-pods` | Yes | No | Yes: the first half of the zone's slot, addresses handed to the nodes in batches of sixteen; the NSGs tell pods from nodes |
| `snet-<zone>-ilb` | Internal load balancers of the applications' `LoadBalancer` Services | Internal load balancer of the zone's gateway (internal zones; an external zone's gateway has a public load balancer, [section 3.1](3.1-cluster-types-stateless-and-stateful.md#external-zones-active-active-with-dns-affinity)) | Same |
| Traffic to another zone of the same cell ([D73](7.2-decisions.md#decision-matrix)) | Everything meets the hub Firewall: pods, nodes and load balancers are in the zone's slot | Node and load balancer addresses meet the Firewall; pod-to-pod between zones is routed by the overlay and is Cilium's alone | Everything meets the Firewall: pods, nodes and load balancers are in the zone's slot |

Zone isolation works the same with every CNI mode because every zone has its own nodes in its own node subnet (a NAP
`NodePool` whose `AKSNodeClass` points at the zone's subnet, or AKS node pools in the stateful cluster and in a
pod-subnet cell): a packet from
a stateless zone that leaves the cluster always carries an address of that zone's subnets (inside an overlay cell the
pods keep their pod addresses between the nodes - below).
Every subnet has its own **NSG** (`nsg-<cell>-<subnet>`, deny-all inbound as the last rule) and every node subnet a
**route table** with BGP propagation off: the system subnet the cell's (`rt-<cell>`), with `0.0.0.0/0` to the
exposure's hub Firewall ([decision D53](7.2-decisions.md#decision-matrix)) as its only route, and each zone's node subnet the
zone's own (`rt-<cell>-<zone>`), with the same default route **plus a route per other zone's slot** - every slot 1 to
14 but the zone's own, occupied or free - to the same Firewall ([decision D73](7.2-decisions.md#decision-matrix)). The default
route alone does not do that: a packet to another slot of the cell matches the VNet's own system route, which is more
specific than `0.0.0.0/0`, and is delivered inside the VNet without any firewall seeing it (what ran until 2026-10-18,
when the design still claimed three layers). A slot's route is more specific than the VNet's, so what one zone sends
to another zone's nodes or load balancers leaves for the Firewall, which denies and logs it - nothing is allowed
between zones ([R5](1.2-requirements.md), [section 2.4](2.4-allowed-and-blocked-flows.md)). Three prefixes stay on the
VNet's route on purpose: the zone's **own slot** (Azure applies a route to the traffic within a subnet as well, and the
nodes of one zone talk to each other directly), **slot 0**, the system subnet (the kubelet tunnel, metrics-server and the
API server's private endpoint are the platform's flows ① to ④, and every zone's gateway pods run there), and slot 15.
So inside a cell three layers separate the zones, in the order a packet meets them: the Firewall (L3-L7, logged), the
destination subnet's NSG and Cilium - and the Firewall is also the layer for everything that leaves the cell. A flow the
Firewall *allowed* would be hairpinned back into the cell through the hub's peering; one to another zone's gateway is
answered from the system subnet, whose table routes no slot to the Firewall, so the answer would take another way than
the question and the Firewall would drop the flow. That is by design: a zone-to-zone allow is a change to R5, not a
Firewall rule, and would also put the slots' routes on the system subnet's table.

The route tables route **VNet addresses**. In an overlay cell the pods' addresses (`100.201.0.0/16`) are none: Azure
routes them between the nodes in a routing domain of its own, which no route table reaches, so pod-to-pod traffic
between two zones of an overlay cell passes neither the Firewall nor a slot route - the NSG lets the overlay range
through between the node subnets on purpose, and Cilium alone separates the zones' pods. What a pod sends to another
zone's *nodes* or *load balancer* (its gateway) is translated to the node's address and takes the Firewall. In a
pod-subnet cell ([D74](7.2-decisions.md#decision-matrix)) the pods carry their zone's addresses, so there every flow between
zones, pod-to-pod included, meets the Firewall - which is why the pod-subnet cell is the default
([D76](7.2-decisions.md#decision-matrix), [section 5.2](5.2-egress-control-options-and-the-company-firewall.md)): the
countries' separation holds when Cilium does not enforce it, and H16 is answered.
In the stateful cluster the pods and the applications' load balancers sit in the zone's slot, so the slot routes cover
everything.

What the NSGs allow on a node subnet, and from where:

- the kubelet port (TCP 10250) from the cell's system subnet (the AKS tunnel); Cilium health (TCP 4240), ICMP and
  DNS (53) between the cell's node subnets; the overlay pod range `100.201.0.0/16` between the node subnets (pods
  are Cilium's to tell apart, not the NSG's); load balancer probes from `AzureLoadBalancer`; ICMP from the hub
  firewall's address; traffic within the subnet;
- TCP 443 from the **Internet** on the system subnet (every zone's gateway pods run there) and on an external
  zone's node subnet; TCP 443 from **`VirtualNetwork`** on an internal zone's node and load balancer subnets and on
  the system subnet - an NSG rule takes one service tag, and the corporate ranges arrive through the hub as
  `VirtualNetwork`.

> **Why subnets and not separate VNets?** AKS requires all node pool subnets and the API server subnet of one
> cluster to be in the same VNet. Within one cluster, "network per country" is therefore implemented as
> *a subnet slot per zone + NSG + Cilium, with the hub firewall between the slots ([D73](7.2-decisions.md#decision-matrix)) and for
> everything that leaves the cell*, which the security team accepts for countries. Internal and external are not separated this way: they are separate
> clusters in separate subscriptions behind separate hubs ([decisions D52, D53](7.2-decisions.md#decision-matrix)),
> so the picture shows an internal cell; an external cell's VNet (`vnet-prd-ext-stateless-az1`) is the same with
> `ext-fi` and `ext-se` in its slots.
> Should a hard VNet boundary per country ever be required, the same step is taken once more – **one cluster per
> zone** – and the address plan stays the same; option E of [D75](7.2-decisions.md#decision-matrix) takes that step with an
> AKS Automatic cluster per zone ([section 5.2](5.2-egress-control-options-and-the-company-firewall.md#e-automatic-one-aks-automatic-cluster-per-isolation-zone)).
