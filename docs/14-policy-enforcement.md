# 14. Policy enforcement with the Azure Policy add-on

**The AKS-native [Azure Policy add-on](https://learn.microsoft.com/en-us/azure/governance/policy/concepts/policy-for-kubernetes)
is the single policy engine**, enabled by the cluster IaC in every cluster. It runs Gatekeeper, but AKS installs and
upgrades it, and the policies are ordinary Azure Policy definitions and assignments – the same tool that governs the
Azure resources (cluster settings, allowed VM sizes, VNet encryption, local auth disabled, private endpoints only).
No Gatekeeper is installed by Flux.

- **Assignments per environment subscription** (`sub-aks-dev`, `sub-aks-acc`, `sub-aks-prd`), so a new or rebuilt
  cluster gets every policy automatically. Compliance of all clusters is visible in one place (Azure Policy, Defender
  for Cloud).
- **Built-in definitions first**: the Kubernetes pod security *restricted* initiative, allowed images, required
  probes and resource requests, and [deployment safeguards](https://learn.microsoft.com/en-us/azure/aks/deployment-safeguards).
- **Custom definitions** (`Microsoft.Kubernetes.Data` mode) for the platform's own rules, with the constraint or
  mutation template embedded as Base64 in the definition. Templates are kept in the IaC repository and tested in CI
  with `gator verify`; CEL-based definitions (generated as Kubernetes `ValidatingAdmissionPolicy`, evaluated
  in-process) are preferred for new validations where they can express the rule.
- **Rollout dev → acc → prd**: definitions are versioned; a new or changed definition is assigned with effect `audit`
  in dev, then `deny`, then promoted to acc and prd with the rest of the platform change.
- **Exemptions expire.** An Azure Policy exemption always has an owner, a reason, a ticket and an `expiresOn` date
  (at most 6 months). The security agent reports exemptions that expire within 30 days, and renewing one is a new
  pull request in the high tier ([section 15](15-ai-driven-day-2-operations.md#risk-tiers)). Exceptions should stay
  visible and a little uncomfortable, not pile up silently.
- **Continuous evidence, not a one-time hardening.** The compliance state of the assignments is the drift signal.
  Next to it, a weekly CIS Kubernetes benchmark scan of the nodes (kube-bench as a platform `CronJob` in
  `infra-security`, the only workload with read-only `hostPath` and `hostPID` besides the platform DaemonSets) and
  the Defender for Cloud secure score per environment go to Grafana Cloud. A *drop* in either raises an alert to the
  security agent, which matters more than the absolute score. The CIS AKS benchmark and the NSA/CISA Kubernetes
  hardening guidance are the reference controls, and the checklist is repeated with every Kubernetes minor upgrade,
  because new minors can change defaults.
- **Platform namespaces**: `kube-system` and `gatekeeper-system` are excluded by the add-on; `flux-system` and other
  platform namespaces are excluded from application rules through the definitions' namespace exclusion parameters.
  The zones' own platform namespaces, `<zone>-gateway` (the zone's App Routing gateway) and `<zone>-secrets`
  (External Secrets Operator), run on the system pool so that a zone without applications has no nodes
  ([section 4](04-node-pools.md)); they are excluded from zone pinning and the other application rules, and their
  policies are the platform's own. The `<zone>-gateway` namespaces enforce the Pod Security Standard *baseline* and
  only audit and warn on *restricted*: App Routing's gateway pods set no seccomp profile, and their `securityContext`
  cannot be customised.
- **Mutations fill in, validations decide.** A mutation only adds what a pod leaves out, so a pod that states its
  placement differently is not changed but reported (audit) or refused (deny) by the matching validation. A
  recorded exception is visible the same way: a pod labelled `platform/zone-placement: "off"` is skipped by the
  zone mutation and stays non-compliant in the zone validation.
- **Which clusters a rule reaches** is set by the assignment, not the definition: a `Microsoft.Kubernetes.Data`
  rule can test only a cluster's type, location and tags. The stateless rules leave out the stateful cluster with
  `notScopes`, and the stateful rules leave out the stateless cells. Custom mutations cannot be parameterized, so the zone
  mutations are one definition per zone, generated by the IaC.

Limits of the add-on and how the design handles them:

| Limit | Consequence in this design |
|---|---|
| Needs `data.policy.core.windows.net`, `store.policy.core.windows.net`, `dc.services.visualstudio.com` (+ Entra ID); no Private Link | Firewall application rules for these FQDNs, also from the stateful cluster (exception to "no Internet", see [flows](08-cluster-types-stateless-and-stateful.md#flows-between-frontend-and-backend)) |
| Custom definitions cannot use Gatekeeper data replication (no lookups of other objects) | Zone rules match the namespace name prefix `<zone>-*`; "PDB exists for every Deployment / StatefulSet" is checked in CI on the rendered manifests, because Flux and the stateful pipeline only apply validated artifacts |
| Policies are synced from Azure every 15 minutes | The stateless cluster bootstrap keeps the Flux `apps` Kustomization suspended until all assigned constraint templates and constraints are present in the cluster; the stateful pipeline checks the same before every run |
| Gatekeeper config cannot be changed | No custom Gatekeeper settings; defaults are fine for this design |
| Max 10 000 pods per cluster | Well above the expected size; monitored |

**Day-1 set.** The first cluster of any environment is accepted only with these rules in `deny` (they are the
acceptance checklist of a new cell; today's dev lab runs every mutation and already denies the storage, FQDN egress, Gateway, NodePool, placement label, ESO, ServiceAccount, rollout, VPA, Ingress and read-only root filesystem rules):
zone placement from the namespace (mutation and validation), `platform/arch` and `platform/capacity` mutations,
images by digest from the environment's ACR, Secrets only through ESO and no Secrets Store CSI, FQDN-only egress,
`PersistentVolumeClaim` rejected in stateless cells, Gateway and HTTPS-only listener rules, `LoadBalancer` and
`NodePort` only in `<zone>-gateway`, NAP `NodePool` and `AKSNodeClass` constraints, requests and probes set, the
*restricted* pod security standard, and the cluster-level rules (Cilium with ACNS, Azure Linux, eBPF host routing,
local accounts and SSH off, CMK). Everything else in the table starts in `audit` and is promoted rule by rule.
