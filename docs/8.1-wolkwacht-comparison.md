# 8.1 Comparison with Wolkwacht

[Wolkwacht](https://wolkwacht.nl) is the blog of Jurgen Allewijn (Microsoft MVP for Azure and Kubernetes). It covers
AKS architecture, security, multi-cluster operations and digital sovereignty. All 50 posts published by
**12 October 2026** were reviewed; the ones that bear on the platform were read in full and compared with this
design. Most of the blog's recommendations are generic AKS
guidance, written for a single cluster or a small fleet. This design is a multi-cluster platform with stricter
isolation and portability requirements, so a difference is not automatically a gap.

The comparison falls into two groups - **agreements**, where the blog and the design reach the same conclusion, and
**deliberate differences**, where the design chooses otherwise for a reason that follows from its requirements. What
the blog raised and the design had not covered (local accounts, SSH, the instance metadata service, image signatures,
a hardened pod baseline, CIS drift, Image Cleaner, expiring exemptions, detections with owners, tested break-glass,
cost efficiency ratios, portability of policy and identity, sovereignty, Chaos Mesh) is in the design now, where each
belongs.

## Agreements

| Topic | Wolkwacht | This design |
|---|---|---|
| API server | Private cluster, Entra ID with Azure RBAC, least privilege, cluster-admin only for emergencies ([Secure AKS](https://wolkwacht.nl/posts/secure-azure-kubernetes-service-aks/)) | Private, VNet-integrated API server reached only from the management VNet; Entra ID, PIM, read-only humans ([section 2.2](2.2-control-plane.md)) |
| Workload credentials | Entra Workload ID, no long-lived secrets in the cluster | Workload identity first, local auth disabled on the PaaS services ([section 2.5](2.5-workload-identity-and-secrets.md)) |
| Secrets for a platform team | ESO is the better paved road for a platform, *if* it comes with scoped stores, separate identities, restricted `Secret` reads, a KMS posture, stale-sync alerts and tested reloads ([Secrets showdown](https://wolkwacht.nl/posts/2026-09-05_secrets-management-showdown--azure-key-vault-csi-driver-vs-external-secrets-operator/)) | ESO per zone with every one of those controls: one `SecretStore` per namespace, a separate reader identity per application, ABAC, KMS with customer-managed keys, `SecretSynced` alerts, volume mounts that reload ([section 2.5](2.5-workload-identity-and-secrets.md#delivered-only-by-external-secrets-operator)) |
| Admission policy | Azure Policy add-on, pod security *restricted* initiative, audit first, then deny | The same, as the single policy engine, rolled out audit → deny per environment ([section 2.7](2.7-policy-enforcement.md)) |
| GitOps | Flux, pull-based, drift corrected, clusters rebuilt from Git ([GitOps with Flux](https://wolkwacht.nl/posts/gitops-on-azure-kubernetes-service-building-a-production-ready-platform-with-flux/)) | Flux through the AKS extension, one configuration per cluster and per team namespace, from Git today and from signed OCI artifacts as the target; clusters are cattle ([section 3.3](3.3-keeping-clusters-in-sync.md)) |
| Node OS | Azure Linux: smaller, faster patches ([Security demystified](https://wolkwacht.nl/posts/azure-kubernetes-security-demystified-from-nodes-to-pods/)) | Azure Linux 3.0 on every node ([section 2.3](2.3-node-pools.md)) |
| Network policy | Cilium, deny by default, allow by exception | Cilium default deny inside every cell and three enforcement layers between zones ([section 2.4](2.4-allowed-and-blocked-flows.md)); out of the cluster the hub Firewall decides per zone in the default cell, per-application FQDN policies where a cell runs ACNS ([sections 5.1](5.1-advanced-networking-and-fqdn-egress.md), [5.2](5.2-egress-control-options-and-the-company-firewall.md)) |
| Nodes and autoscaling | NAP is the preferred default; autoscalers are interacting control loops; VPA and HPA must not act on the same signal ([Reducing AKS costs](https://wolkwacht.nl/posts/reducing-aks-costs-autoscaling-spot-nodes-rightsizing-and-finops-practices/)) | NAP in the stateless clusters; VPA controls only the resource the HPA does not scale on ([section 2.3](2.3-node-pools.md#pod-right-sizing-vertical-scaling-in-place)) |
| Spot | Spot is an interruption domain: tolerate it, *prefer* it, fall back to on-demand, and do not count on PDBs | Tainted spot `NodePool`, preferred affinity, on-demand fallback, applications opt in ([section 2.3](2.3-node-pools.md#cpu-architecture-and-spot-chosen-by-the-application)) |
| Encryption at rest | Customer-managed keys; Kubernetes `Secret`s are only base64, so check KMS | CMK for etcd (KMS), node disks and persistent volumes ([section 4.2](4.2-encryption-at-rest-and-customer-managed-keys.md)) |
| Blast radius | Architecture decides how far a failure travels; isolate the management plane; separate production from non-production ([Architecture decides the blast radius](https://wolkwacht.nl/posts/architecture-decides-the-blast-radius/)) | Cells and isolation zones (bulkheads), management VNet, environments in separate subscriptions ([requirements](1.2-requirements.md#cells-and-bulkheads)) |
| Observability across clouds | Vendor-neutral Prometheus and Grafana instead of one cloud's monitoring ([Chronicles 11](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-11-governing-the-chaos/)) | Grafana Cloud with OpenTelemetry for every cluster ([section 6.2](6.2-observability-with-grafana-cloud.md)) |
| Backup and DR | Backups must be tested; DORA requires defined RTO / RPO and recovery tests ([Chronicles 4](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-part-4/)) | Immutable copies in the paired region and a region recovery drill every six months, designed for the stateful cluster and built with it; a stateless cell holds no data and is rebuilt from IaC and Git ([section 6.3](6.3-backup-and-region-recovery.md)) |
| Chaos engineering | Azure Chaos Studio, experiments under load, tied to SLOs ([Harnessing chaos](https://wolkwacht.nl/posts/harnessing-chaos-implementing-chaos-engineering-with-azure-chaos-studio-and-gremlin-on-aks/)) | Chaos Studio in acceptance, every fault under load, each must raise its alert ([section 7.1](7.1-implementation-project-and-acceptance-testing.md#high-availability-and-resilience)) |
| Multi-cluster is the norm | Regulation, resilience and separation of concerns lead to many clusters ([Chronicles 7](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-7-the-multi-cluster-reality/)) | Fourteen to twenty clusters per platform: one cell per availability zone and exposure, internal and external in separate subscriptions ([section 3.2](3.2-environments.md)) |

## Deliberate differences

| Topic | Wolkwacht recommends | This design | Why |
|---|---|---|---|
| Kubernetes and node image upgrades | Auto-upgrade channel `stable` plus node OS channel `NodeImage`, or AKS Automatic, which manages upgrades for you | Channel `none` in the stateless cells; a version pipeline with two speeds, applied only while a cell is drained ([section 3.5](3.5-zero-downtime-cluster-upgrades.md#update-policy)) | Nothing may change a cell outside the drain → change → test → return procedure (R12), and one cell must always run a version already proven in prd (R12a). The blog's own concern – a new node starting from an old image – is answered by pinning the image per cell ([decision D11](7.2-decisions.md#decision-matrix)) |
| Secrets delivery | The Secrets Store CSI driver as the secure default for applications that read files ([Secure AKS](https://wolkwacht.nl/posts/secure-azure-kubernetes-service-aks/)) | CSI disabled; ESO only (R7b) | One delivery path for all applications, pods start during a Key Vault outage, and ESO has providers for every cloud. The blog's later [showdown](https://wolkwacht.nl/posts/2026-09-05_secrets-management-showdown--azure-key-vault-csi-driver-vs-external-secrets-operator/) reaches the same conclusion for platform teams |
| Monitoring | Container Insights and Azure Managed Prometheus / Grafana | Grafana Cloud, with Alloy run from Fleet Management; Private Link in the corporate tenant (the lab reaches it over the Internet); the monitoring add-on is not enabled | R22, and the same collector in every cloud |
| Ingress | [Application Gateway for Containers](https://wolkwacht.nl/posts/application-gateway-for-containers-the-future-of-cloud-native-ingress/) as a managed Gateway API implementation, behind Front Door | A Gateway API implementation inside the cell, one `Gateway` per isolation zone on the system pool, chosen per cluster ([D55](7.2-decisions.md#decision-matrix)): AKS App Routing's sidecar-less Istio in acc and prd, Traefik in the dev lab, where istiod's fixed 1 CPU and 4 GiB cost a second system node; no AGC and no Front Door ([section 4.1](4.1-encryption-in-transit-and-tls.md)) | The Azure standard offering where the cell is big enough to pay for it, and open-source Istio or Traefik run in other clouds too. Each zone's entry point (gateway pods, load balancer) is part of its bulkhead. Applications write only `HTTPRoute`s, so they would not change if a cell used AGC instead |
| East-west security | [Azure Kubernetes Application Network](https://wolkwacht.nl/posts/azure-kubernetes-application-network-part-1-what-appnet-is-and-how-to-get-started/): managed Istio ambient, mTLS and authorisation by workload identity and HTTP method / path | No service mesh: VNet encryption between nodes, Cilium policies by namespace and label, Entra ID tokens validated by the applications (R9b) | No sidecars or waypoints to run and upgrade; AppNet is preview, AKS-only, and cannot run next to App Routing's istiod. What is missing without a mesh, what one would cost, and the way in (managed Istio ambient, enrolled per namespace) are written down in [service mesh or not](4.1-encryption-in-transit-and-tls.md#service-mesh-or-not) ([decision D38](7.2-decisions.md#decision-matrix)) |
| Multi-cluster management | [Azure Kubernetes Fleet Manager](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-6/): resource placement and update runs from a hub | Flux per cell and pipelines that drain each cell at Traffic Manager ([section 3.4](3.4-zero-downtime-application-upgrades.md#releases-cell-by-cell)) | Releases and upgrades are tied to draining the cell, which Fleet does not do. Fleet is AKS-only, as the blog itself notes in [Chronicles 8](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-8-fleet-in-focus/). It stays an option with a trigger - more clusters than the train can drain one by one ([section 7.4](7.4-outlook-2030-and-the-options-kept-open.md#the-options-kept-open)) |
| Burst capacity | [Virtual nodes](https://wolkwacht.nl/posts/when-your-cluster-isnt-sufficient-introducing-virtual-pools-in-aks/) (Azure Container Instances) as a pressure relief valve | Not used ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md#cluster-settings)); node auto provisioning is the relief valve, with N+1 capacity per cell | The blog lists the limits itself: no Cilium policies, no DaemonSets. Here that would bypass the zone's network policies, zone pinning and the node-local telemetry |
| eBPF and Advanced Container Networking Services | The CNI and eBPF introductions (Chronicles 1–3) present Azure CNI powered by Cilium with ACNS - eBPF host routing, FQDN filtering, Hubble - as the networking to build on | Azure CNI powered by Cilium in every cell, but ACNS off in the default cell: the hub Firewall decides egress per zone, and FQDN filtering, Hubble and eBPF host routing are per-cell switches with the way in written down ([D61](7.2-decisions.md#decision-matrix), [ACNS in detail](5.2-egress-control-options-and-the-company-firewall.md#acns-and-ebpf-host-routing-in-detail)) | ACNS is billed per node-hour, on the nodes that scale on load; the Firewall per exposure exists in every model and already decides for everything that is not a pod. eBPF host routing is set at cluster creation only and excludes features a future workload may need |
| Kernel-level tracing | [Inspektor Gadget](https://wolkwacht.nl/posts/when-kubernetes-lies/) installed in the cluster as a privileged DaemonSet | Deployed only during an incident, through break-glass ([section 6.2](6.2-observability-with-grafana-cloud.md#security-detections-and-forensics)) | A privileged, cluster-wide tracer is itself a high-value target |
| Backup tool | Velero or Kasten K10 ([Chronicles 4](https://wolkwacht.nl/posts/azure-kubernetes-chronicles-part-4/)) | Azure Backup for AKS, vault tier, locked immutable, once the stateful cluster exists ([section 6.3](6.3-backup-and-region-recovery.md)) | Immutability that an `Owner` cannot undo, and Cross Region Restore. In another cloud, Velero is the portable equivalent |
| Application building blocks | [Dapr](https://wolkwacht.nl/posts/what-is-dapr-and-why-run-it-on-kubernetes/) as a portable API for state, pub/sub and service calls | Not offered by the platform; applications use the open protocols of the PaaS services ([section 1.3](1.3-open-standards-and-portability.md#data-in-paas-services-that-every-cloud-offers)); the AKS Dapr extension is an option kept open, tried in the lab cell az3 ([D65](7.2-decisions.md#decision-matrix)) | Dapr fails D64's tests: nothing names it, and applications notice - the Dapr API becomes their contract. It adds a sidecar per pod (100m / 250 MiB requested by Dapr's guidance), a control plane per cell with state that wants persistent volumes, and its own mTLS and CA, which overlaps with the "no service mesh" rule. The blog also points out that changing the Dapr component does not remove the differences between brokers |
| Agents for operations | The [AKS-MCP server](https://wolkwacht.nl/posts/using-the-aks-mcp-server-in-day-to-day-operations/) with Contributor or cluster-admin, so an assistant can scale or deploy | Agents read only and change everything by pull request ([section 6.1](6.1-ai-driven-day-2-operations.md)); the egress and documentation agents built so far open pull requests that a human merges | Git is the only write path (R18). AKS-MCP fits as the agents' read-only tool layer |
| Adopting new AKS features | Each post evaluates a feature on its own merits, and most end with "use it" | A feature is added only by the five tests of [D64](7.2-decisions.md#decision-matrix): something names it, the cloud manages it, it is a per-cell switch, applications do not notice, the way out is written first ([section 7.4](7.4-outlook-2030-and-the-options-kept-open.md)) | A single-cluster blog can adopt a feature in an afternoon; a fleet of fourteen to twenty clusters pays for every feature in every cell, every upgrade |

## Questions it raised

Recorded in the [decision log](7.2-decisions.md), each with a decision or a verification: whether signature checks at promotion are enough while Image
Integrity can only audit; identity-based east-west authorisation and Application Network; the policy engine and data
plane in a second cloud; sovereignty and a European exit target; Azure-only PaaS services that sections 2.5, 3.1 and 6.3
still list but section 1.3 excludes; Container Apps for small workloads; GPU and AI inference workloads; Chaos Mesh,
Inspektor Gadget, kube-bench and Image Cleaner compatibility; SSH and local accounts on NAP nodes and add-ons. The
features the blog recommends and the design leaves out - a mesh, ACNS in every cell, Fleet Manager, virtual nodes -
are in the [options kept open](7.4-outlook-2030-and-the-options-kept-open.md#the-options-kept-open), each with the
trigger that would bring it in.
