# 7.2 Decisions

This page is the decision log of the design: what was decided, which options were weighed, why, and what still
needs a named human. Two external reviews ([issue 7](https://github.com/onek8s/onek8s.github.io/issues/7),
[issue 8](https://github.com/onek8s/onek8s.github.io/issues/8)) asked for it in place of the long list of
[open questions](7.3-open-questions.md); everything they raised is settled in the sections or recorded here. The sections
of the design stay the specification; this page says *why* they read as they do and which choices are still
provisional.

**How to read the tables**

| Status | Meaning |
|---|---|
| **Decided** | Justified below, reflected in the sections, no human action needed. Re-opened only by a design pull request. |
| **Decided – confirm** | The design has chosen a default and is built on it, but the choice spends money, accepts a risk or binds another team, so a named role must sign it off ([human sign-offs](#human-sign-offs-still-needed)). |
| **Verify** | No decision to make; an assumption about Azure that the dev lab or acceptance ([section 7.1](7.1-implementation-project-and-acceptance-testing.md)) proves or disproves ([capability matrix](#azure-capability-and-verification-matrix)). |
| **Open** | Only a human can answer it (business targets, regulation, corporate IPAM). The design states the default it assumes meanwhile. |

**Criteria** used to justify a decision, in the order the platform weighs them when they conflict:

| Code | Criterion |
|---|---|
| **Sec** | Security: least privilege, smaller blast radius, defence in depth |
| **Auto** | Maximum automation: no manual steps, no human in loops that must react in minutes |
| **Std** | Industry standard, or the Azure standard offering that AKS manages and upgrades |
| **Simple** | Fewer moving parts to run, patch and reason about |
| **Cost** | Lower steady-state or failure-mode cost |
| **Port** | Portability: open standards, the same platform in another cloud ([section 1.3](1.3-open-standards-and-portability.md)) |

## Decision matrix

|---|---|---|---|---|---|
| D01 | Cluster granularity | (a) One cluster per cell with isolation zones inside; (b) one cluster per zone (or per country) | **(a) within one exposure** since [D52](#decision-matrix): the country zones of an exposure are address spaces, subnets, NSGs, UDRs, nodes, vaults and policies inside one cluster per cell ([section 2.1](2.1-network-layout.md)); internal and external are separate clusters | Cost, Simple: one control plane, one Flux, one gateway control plane per cell and exposure instead of one per zone. Sec is kept with three enforcement layers (NSG, Firewall, Cilium) and tested negatively; the security team accepts node pool + network as the boundary between countries (2026-10-14). (b) stays the documented escalation if a regulator demands a hard VNet boundary per country | Decided (security, 2026-10-14) |
| D02 | Address plan | (a) `/12` per environment, `/16` per country, `/17` per zone; (b) `/17` per country when the corporate plan cannot spare it | **(a)** assumed; the structure works one level smaller ([address plan](3.1-cluster-types-stateless-and-stateful.md#vnets-and-address-plan)) | Simple: one summarisable prefix per zone across all clusters keeps every Firewall rule stable. Only the size is the corporate IPAM's call | Open ([H02](#human-sign-offs-still-needed)) |
| D03 | Cluster DNS | (a) CoreDNS on the system pool, shared by all zones; (b) CoreDNS per zone; (c) NodeLocal DNS | **(a)** | Std, Simple: AKS manages CoreDNS; DNS is one of the few flows R5 allows between zones by design ([flow ③](2.4-allowed-and-blocked-flows.md)); the FQDN policies' DNS proxy already sits in every pod's path. | D04 | Web application firewall for external zones | (a) No WAF: Traffic Manager (DNS only), DDoS protection, NSG 443 only, gateway, Cilium ingress, application-level controls; (b) Application Gateway WAF v2 per external zone and cell in front of the gateway; (c) Front Door Premium WAF | **(a) at launch**, with (b) as the defined add-on ([section 3.1](3.1-cluster-types-stateless-and-stateful.md#external-zones-active-active-with-dns-affinity)) | (c) was rejected with Front Door (TLS must end in the cell, DNS affinity). | D05 | Release cadence | (a) One fleet release train per environment per day; (b) continuous per-application releases; (c) in-cell progressive delivery | **(a)** with the emergency fast track; (c) only for strictly backwards-compatible back-end APIs ([section 3.4](3.4-zero-downtime-application-upgrades.md#releases-cell-by-cell)) | Auto: the train is a pipeline, not a meeting. | D06 | External client affinity | (a) Traffic Manager Subnet routing (affinity by client network); (b) cookie affinity in a layer-7 router; (c) no affinity | **(a)**, treated as an optimisation: the [compatibility rule](3.4-zero-downtime-application-upgrades.md) is the correctness guarantee | Simple, Sec: no stateful component in front of the cells, TLS ends in the cell.
