# 7.3 Open questions

Everything the design once listed as open is now a recorded decision, a verification acceptance performs, or a
question only a human can answer - all three in the [decision log](7.2-decisions.md): the
[sign-offs](7.2-decisions.md#human-sign-offs-still-needed) H01-H15 with the role that answers each and the default
assumed meanwhile, and the [capability matrix](7.2-decisions.md#azure-capability-and-verification-matrix) V03-V32 with
what acceptance has to show. This page keeps only the questions that are neither: features a
person has to weigh before the design takes or refuses them.

## Recently added features not yet adopted

Kubernetes 1.36 (April 2026), 1.37 (August 2026, AKS GA October 2026) and AKS's 2026 releases were reviewed on
2026-10-18 against the [rule for adding a feature](7.4-outlook-2030-and-the-options-kept-open.md#keep-it-simple-the-rule-for-adding-a-feature)
([D64](7.2-decisions.md#decision-matrix)). What passed is in the design ([D67](7.2-decisions.md#decision-matrix): idle
volumes in the stateful cluster; node pool rollback in [section 3.5](3.5-zero-downtime-cluster-upgrades.md#stateful-cluster);
`externalIPs` denied in [section 2.7](2.7-policy-enforcement.md); the 1.37 checklist V26). What failed for good is in
the [options kept open](7.4-outlook-2030-and-the-options-kept-open.md#the-options-kept-open). The rows below are
the ones a person has to decide, each with the design's default until then and what would settle it.

| # | Feature (status) | Options | Default until decided | What settles it | Who |
|---|---|---|---|---|---|
| Q01 | **LocalDNS** - AKS's node-level DNS proxy, switched on by AKS itself from 1.37 "where the networking supports it"; incompatible with ACNS FQDN filtering; [D03](7.2-decisions.md#decision-matrix) chose CoreDNS alone | (a) `Disabled`, stated on every node pool ([section 2.3](2.3-node-pools.md)); (b) `Required` in the cells without ACNS (the [D61](7.2-decisions.md#decision-matrix) default), `Disabled` where FQDN policies run; (c) `Preferred` - AKS decides per minor | **(a)**: the version pipeline decides what changes in a cell, not a minor's default | A DNS latency or failure measurement in acceptance that CoreDNS alone cannot meet; a proof that the zones' Cilium DNS rules (to kube-dns) and the egress policies hold with the node-local proxy on the host; a cell that mixes ACNS and non-ACNS zones is not possible either way | Platform architect |
| Q02 | **Workload identity inside the cluster without a mesh** - `PodCertificateRequest` and `ClusterTrustBundle` GA in 1.37 ([section 4.1](4.1-encryption-in-transit-and-tls.md#service-mesh-or-not)); AKS ships no signer | (a) Nothing: VNet encryption in transit, identity at the gateway and in Entra ID ([D38](7.2-decisions.md#decision-matrix)); (b) a signer the platform runs (one controller, SPIFFE-shaped names from namespace and ServiceAccount), applications terminate TLS themselves - a second control plane and a change in the application contract; (c) AKS's managed Istio in ambient mode when the day comes (the path in [section 7.4](7.4-outlook-2030-and-the-options-kept-open.md#the-options-kept-open)) | **(a)**; (c) before (b) unless AKS offers a signer | A regulation or customer asking for authentication between workloads, the same trigger as the mesh row; AKS offering a managed signer would make (b) pass D64 | Security team |
| Q03 | **User namespaces** for application pods - GA in 1.36, on AKS since 1.33 with Azure Linux 3.0 "without configuration" (`hostUsers: false`): root in the container is an unprivileged user on the node, a second line behind the *restricted* pod security standard ([section 2.6](2.6-application-multi-tenancy.md)) | (a) Not used; (b) the zone mutation sets `hostUsers: false` on every application pod, opt-out by label with a reason; (c) opt-in by a pod label, the onboarding agent proposes it | **(a)** until a cell has run it; the design leans to (b) for new namespaces once proven | A dev cell running the reference application, a volume of each StorageClass (idmapped mounts: ephemeral and Azure Disk yes, Azure Files to prove), Beyla's attribution and the VPA's in-place resize with user namespaces on; the pentest or CIS naming it would settle (b) | Security team, platform architect |
| Q04 | **HPA scale to zero** - beta and on by default in 1.37, for custom and external metrics only (CPU and memory cannot reach zero) | (a) KEDA when a team scales on events, as [section 3.4](3.4-zero-downtime-application-upgrades.md) says (not deployed); (b) plain HPA with `minReplicas: 0` on an external metric, KEDA or another adapter only as the metrics source; (c) both, documented as one pattern | **(a)**, nothing changes: an event-driven team still needs the metrics adapter, which is KEDA | The first team that asks for scale-to-zero: whether its source has a KEDA scaler; the rollout guardrails already allow 0 replicas (an application switched off) and refuse 1 | Platform architect |
| Q05 | **Storage of the stateful cluster** - Azure Container Storage v2 (GA; local NVMe, and Elastic SAN with ZRS since 2.1, April 2026; Azure Disk stays on v1) and `VolumeGroupSnapshot` (GA in 1.36: a crash-consistent snapshot of several volumes at once) | (a) Azure Disk `Premium_ZRS` / `StandardSSD_ZRS` and Azure Files ZRS through the zone StorageClasses ([section 3.1](3.1-cluster-types-stateless-and-stateful.md#comparison)); (b) Elastic SAN ZRS through Container Storage v2 for the volumes, when the exception needs more IOPS per node than disks attach; (c) local NVMe only for a workload with its own replication (a database with three replicas) | **(a)**; (b) and (c) per exception | The first approved stateful exception's IOPS, latency, attach-count and backup needs ([section 6.3](6.3-backup-and-region-recovery.md)); whether Azure Backup for AKS and the Azure Disk CSI driver take `VolumeGroupSnapshot` for a StatefulSet with several volumes | Platform architect with the exception's owner |
| Q06 | **The system pool** - AKS's managed system node pool (conversion of a Standard cluster in preview since September 2026): AKS sizes, patches and guards the system nodes (no SSH keys, no port-forward there, `kube-system` Secrets unreadable, a built-in `externalIPs` block); also in preview: custom `kube-reserved` and eviction thresholds, and an in-place VM size change of a pool | (a) The platform's own system pool - two nodes per cell ([section 3.2](3.2-environments.md#cost-and-capacity-model)); (b) the managed system node pool once it converts a Standard cluster in GA, if it accepts the cells' subnet, CMK, Azure Linux and the zone gateways and ESOs on it; (c) keep (a) and tune `kube-reserved` when it is GA | **(a)** | The system node's memory in acceptance; (b) needs the conversion GA and a dev cell that proves the platform pods still fit and the policies still apply there | Platform architect |
| Q07 | **Node OS of the stateful cluster** - Azure Container Linux (GA on AKS from 1.34, May 2026: image-based, immutable, the successor of Flatcar and of Azure Linux with OS Guard, which retires December 2026) next to Azure Linux 3.0 with the `SecurityPatch` channel ([D10](7.2-decisions.md#decision-matrix), V13 open) | (a) Azure Linux 3.0, `SecurityPatch` in place, `NodeImage` if refused (the design); (b) Azure Container Linux, every patch a new image rolled with the surge settings - no in-place patching, no drift, but every patch a node replacement on long-lived stateful nodes; (c) (b) only for the system pool | **(a)** until V13 is answered on a network isolated cluster | V13's result; whether eBPF host routing, Image Integrity and the CIS node checks run on Azure Container Linux (eBPF host routing requires Azure Linux today) | Platform architect, security team |
