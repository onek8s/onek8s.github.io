# 1.2 Requirements

Every requirement below has a test: the isolation and requirement tests of
[section 7.1](7.1-implementation-project-and-acceptance-testing.md#requirement-and-isolation-tests) are tagged with the
requirement number they cover and run after every change of a cell. Why the design meets a requirement the way it
does, and which choices still wait for a human, is in the [decision log](7.2-decisions.md).

| # | Requirement | How the design meets it |
|---|---|---|
| R1 | Control plane in a dedicated network | Private, VNet-integrated API server in its own delegated subnet; admin access only via Private Link from a separate management VNet ([picture 2.2](2.2-control-plane.md)) |
| R2 | Internal and external workloads isolated – at subscription and cluster level (security, 2026-10-14) | A subscription per environment and exposure (`sub-aks-<env>-int`, `sub-aks-<env>-ext`), each with its own clusters, VNets, Key Vaults, ACR and policy assignments; zones `int-*` only in internal clusters, `ext-*` only in external ones ([section 3.1](3.1-cluster-types-stateless-and-stateful.md#internal-and-external-separate-subscriptions-and-clusters), [decision D52](7.2-decisions.md#decision-matrix)) |
| R3 | Workloads of different countries isolated – node pool and network are enough | Separate isolation zones per country (`*-fi`, `*-se`, …) inside the clusters of each exposure |
| R4 | Isolation = Key Vault + network + node pool per type | Every zone has its own Key Vault, subnets (NSG + route table) and nodes – a node auto provisioning `NodePool` in the stateless clusters, AKS node pools in the stateful cluster ([section 2.3](2.3-node-pools.md)); certificates are the one shared exception, kept in the per-environment platform Key Vault with a role assignment per certificate |
| R5 | Only connectivity mandatory for Kubernetes allowed between zones | Deny-by-default on three layers: NSG, Azure Firewall, Cilium network policy ([picture 2.4](2.4-allowed-and-blocked-flows.md)) |
| R6 | Applications isolated in namespaces + network policies | Namespace per application, default-deny policies ([picture 2.6](2.6-application-multi-tenancy.md)); egress out of the cluster only through the application's FQDN policy (R20) |
| R7 | Key Vault multi-tenancy with [Azure RBAC + ABAC](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-abac) | Per-application secret reader identity, usable only by External Secrets Operator, with secret-name-prefix conditions ([picture 2.5](2.5-workload-identity-and-secrets.md)) |
| R7a | Workload identities wherever possible, secrets only when needed | Per-application workload identity with Entra ID auth to all Azure services, local auth disabled by Azure Policy; Key Vault secrets only for targets without Entra ID ([section 2.5](2.5-workload-identity-and-secrets.md)) |
| R7b | Applications never read Key Vault directly; External Secrets Operator is mandatory for them | One ESO controller per zone reads Key Vault on behalf of the applications; the zone's gateway uses ESO like an application; other platform components may use Key Vault directly with their own workload identity and narrow roles; the Secrets Store CSI driver add-on is disabled; application identities have no Key Vault role, application pods cannot use the reader identity or reach a vault, and only ESO may write Secrets in application namespaces ([section 2.5](2.5-workload-identity-and-secrets.md#delivered-only-by-external-secrets-operator)) |
| R8 | Two cluster types: stateless and stateful | Per exposure, stateless clusters in the frontend network and one optional stateful cluster in the backend network, built only when a workload requires it ([picture 3.1](3.1-cluster-types-stateless-and-stateful.md)) |
| R8a | Stateful cluster is the last option | Placement order stateless cluster → Azure PaaS → stateful cluster; the stateful cluster needs a documented exception ([where does a workload run](3.1-cluster-types-stateless-and-stateful.md#where-does-a-workload-run)) |
| R9 | Stateful cluster exists at most once per exposure (R2), in the backend network with the Azure PaaS services, **no Internet egress and no public endpoints**; the only outbound destinations outside Private Link are allow-listed Microsoft control-plane endpoints that have no Private Link (Entra ID for workload identity, the Azure Policy add-on) | Backend spoke with PaaS private endpoints; network isolated AKS (outbound type `none`), no public IPs, Firewall deny-all for backend prefixes except the two allow-listed destinations, tested from the cluster and by Resource Graph ([flows](3.1-cluster-types-stateless-and-stateful.md#flows-between-frontend-and-backend), [decision D09](7.2-decisions.md#decision-matrix)) |
| R9a | Stateful cluster: VNet-integrated CNI, no Gateway API implementation (and no Ingress), applications handle TLS | Azure CNI (VNet, dynamic pod IP allocation) powered by Cilium with ACNS; applications are published with internal `LoadBalancer` Services and terminate TLS themselves ([section 4.1](4.1-encryption-in-transit-and-tls.md)) |
| R9b | Stateless clusters: overlay CNI, no service mesh / mTLS / application TLS, TLS-only Gateway API (no Kubernetes Ingress) | Azure CNI Overlay powered by Cilium with ACNS and eBPF host routing, Azure Virtual Network encryption between nodes, AKS App Routing's Gateway API implementation (`approuting-istio`, sidecar-less Istio control plane, not a mesh) with Let's Encrypt certificates for internal DNS names, distributed through Key Vault, and HTTPS-only listeners ([section 4.1](4.1-encryption-in-transit-and-tls.md)) |
| R10 | Stateful cluster spread over availability zones and running AKS LTS | Fixed-size node pools per AZ 1/2/3 (no autoscaling), ZRS storage, Premium tier with Long Term Support |
| R11 | Stateless: separate cluster per availability zone (at least two), ≥ 2 copies of every application, scaled on load | `sl-az1`, `sl-az2` (+ optional `sl-az3`); external applications in every cell behind a zone-redundant traffic layer, internal applications in one home cell each, migrated to another cell on failure; policy-enforced replicas ≥ 2, HPA/KEDA, VPA in-place right-sizing ([section 2.3](2.3-node-pools.md#pod-right-sizing-vertical-scaling-in-place)), [node auto provisioning](https://learn.microsoft.com/en-us/azure/aks/node-autoprovision) (NAP) |
| R12 | Fully automated zero-downtime upgrades of applications and clusters | Policy-enforced rollout guardrails, releases one cell at a time with DNS affinity (external zones), zero-downtime migration of internal applications between cells, pipeline-driven stateful rollout, drain-and-upgrade per stateless cluster, PDB-guarded per-AZ upgrade of the stateful cluster ([section 3.4](3.4-zero-downtime-application-upgrades.md), [section 3.5](3.5-zero-downtime-cluster-upgrades.md)) |
| R12a | Update policy: stateful cluster only when absolutely necessary, stateless clusters at two speeds | Every cluster starts on 1.36, the platform floor. Stateful: created on the second latest GA minor (N-1), then kept on that minor with LTS until 6 months before its end of LTS support, existing nodes patched instead of replaced where possible. Stateless: `sl-az1` on the second latest minor with patches after 1 week per environment, `sl-az2` one minor behind with 3 weeks per environment (shortened from 1 month because NAP forces node images older than 90 days, [decision D11](7.2-decisions.md#decision-matrix)); node images pinned per cell ([update policy](3.5-zero-downtime-cluster-upgrades.md#update-policy)) |
| R13 | dev, acc and prd environments kept in sync | 2 exposures × (2 + 2 + 3) = 14 clusters (20 with the stateful clusters) from the same IaC modules, all in-cluster state from one Git repository: FluxCD in the stateless clusters, CI/CD pipeline in the stateful cluster ([picture 3.2](3.2-environments.md), [picture 3.3](3.3-keeping-clusters-in-sync.md)) |
| R14 | One policy engine | Azure Policy add-on for AKS in every cluster, assigned per environment subscription; the same Azure Policy also governs the Azure resources ([section 2.7](2.7-policy-enforcement.md)) |
| R15 | Certificates distributed through Key Vault, shared by all clusters | One shared **platform Key Vault per environment and exposure** (`kv-<env>-<exposure>-platform`) holds all certificates of that exposure's zones; a renewal job per environment issues one certificate per zone into the vault of the zone's exposure, and External Secrets Operator in every cluster of the exposure reads it with plain Azure RBAC scoped to the individual certificate ([section 4.1](4.1-encryption-in-transit-and-tls.md#certificates-issued-centrally-distributed-through-the-platform-key-vault)) |
| R16 | Countries can be added online | One address space per zone in every cluster VNet, taken from a per-country prefix; a new country adds address spaces, subnets and NAP `NodePool`s / node pools; existing zones only get new routes and Firewall rules ([VNets and address plan](3.1-cluster-types-stateless-and-stateful.md#vnets-and-address-plan)) |
| R17 | Cost-optimised compute: applications choose amd64 or arm64 and on-demand or spot nodes, the platform supports all of them | Stateless clusters: pod labels `platform/arch` (`amd64` / `arm64` / `multi`) and `platform/capacity` (`on-demand` / `spot`), turned into node selection by Azure Policy mutation; per zone an on-demand and a tainted spot NAP `NodePool` with amd64 + arm64 SKUs and fallback to on-demand; defaults amd64 on-demand; stateful cluster on-demand amd64 only ([section 2.3](2.3-node-pools.md#cpu-architecture-and-spot-chosen-by-the-application)). GPUs on request: `platform/accelerator: nvidia-gpu` and an `nvidia.com/gpu` request put the pod on the zone's GPU `NodePool`, which scales to zero ([decision D42](7.2-decisions.md#decision-matrix)) |
| R18 | Day 2 operations driven by AI agents, also in prd, but only through GitOps / IaC pull requests within human-defined guardrails | Agents with read-only identities per agent and environment open pull requests; a merge gate owned by humans computes a risk tier from the plan and requires checks and 0–2 human approvals; only the existing deployment identities write; runtime guardrails unchanged ([section 6.1](6.1-ai-driven-day-2-operations.md)) |
| R19 | AKS advanced networking with eBPF host routing | [Advanced Container Networking Services](https://learn.microsoft.com/en-us/azure/aks/advanced-container-networking-services-overview) (`--enable-acns`) in every cluster; eBPF host routing (`--acns-datapath-acceleration-mode BpfVeth`) on Azure Linux 3.0 nodes in every cluster from day one (every cluster starts on 1.36, so ≥ 1.33); no host iptables, no Static Egress Gateway ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md)) |
| R20 | Applications must define an FQDN-based egress policy for any traffic exiting the cluster | Platform baseline puts every application pod in Cilium default-deny egress; the application's own `CiliumNetworkPolicy` `egress` lists every external destination with `toFQDNs` + ports and a matching DNS rule; Azure Policy rejects CIDR / entity egress, broad wildcards and custom DNS; CI checks the names against the zone's Firewall allow-list ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md)) |
| R21 | Data at rest encrypted with customer-managed keys: own key for each control plane and each node pool, stored in the platform Key Vault | Keys in the platform vault of the cluster's exposure, `kv-<env>-<exposure>-platform`: per cluster a KMS etcd key (control plane) and an OS-disk key (disk encryption set for all its nodes – AKS supports only one per cluster, not per node pool); in the stateful cluster also one key per isolation zone for its persistent volumes; encryption at host on every node ([section 4.2](4.2-encryption-at-rest-and-customer-managed-keys.md)) |
| R22 | Observability, including tracing, with Grafana Cloud; anyone allowed to connect to it may see all data | One Grafana Cloud stack per environment for metrics, logs, traces, SLOs, alerting, on-call and synthetic monitoring; Grafana Alloy on every node collects node-locally and sends through Azure Private Link (also from the Internet-less stateful cluster); Entra ID sign-in, and every user of a stack sees all of its data, so secrets and data the users may not see are never sent; Azure-produced logs stay in Log Analytics and are read in place ([section 6.2](6.2-observability-with-grafana-cloud.md)) |
| R23 | Protect against losing the region with immutable backups in another region; back up only persistent data, not whole clusters | Every PaaS data store, the stateful cluster's persistent volumes and the Key Vault secrets that cannot be issued again are backed up into the Azure paired region, in locked immutable Backup vaults (Cross Region Restore) and locked immutable storage accounts in a backup subscription per environment; clusters, Kubernetes objects and images are rebuilt from IaC and Git; region recovery declared by humans and drilled in acc ([section 6.3](6.3-backup-and-region-recovery.md)) |
| R24 | Every application has health probes, and every application published through a gateway a health endpoint the platform probes | Readiness and liveness (+ startup) probes required on every application container and enforced by admission policy ([section 3.4](3.4-zero-downtime-application-upgrades.md), [section 2.7](2.7-policy-enforcement.md)); applications behind a gateway answer HTTPS `GET /healthz` with 200 only while they can serve, through each cell's gateway with the application's host name – Traffic Manager (external zones) and Grafana Cloud synthetic monitoring probe it per cell and leave out a cell whose probe fails ([section 3.1](3.1-cluster-types-stateless-and-stateful.md), [section 6.2](6.2-observability-with-grafana-cloud.md)) |
| R25 | Every workload's owner and cost are known | Every namespace carries `platform/team`, `platform/cost-center` and the annotation `platform/contact`, set at onboarding and required by Azure Policy; OpenCost splits each cell's cost by namespace and so by team and cost centre, in Grafana Cloud; a monthly budget per environment subscription alerts the owners at 80 % and 100 % ([section 2.6](2.6-application-multi-tenancy.md#ownership-and-cost), [decisions D46, D47](7.2-decisions.md#decision-matrix)) |

**Exposure** = internal (`int`) or external (`ext`): its own subscription and clusters per environment (R2).
**Isolation zone** = one *type* = one combination of exposure × country, inside the clusters of its exposure:

| Zone | Exposure (subscription, clusters) | Country | NAP `NodePool` (stateless) | Node pools (stateful) | Key Vault (one per environment) | Subnets |
|---|---|---|---|---|---|---|
| `int-fi` | internal (`sub-aks-<env>-int`, `aks-<env>-int-*`) | FI | `intfi`, `intfispot` | `intfiz1`–`z3` | `kv-<env>-int-fi` | `snet-int-fi-*` |
| `int-se` | internal (`sub-aks-<env>-int`, `aks-<env>-int-*`) | SE | `intse`, `intsespot` | `intsez1`–`z3` | `kv-<env>-int-se` | `snet-int-se-*` |
| `ext-fi` | external (`sub-aks-<env>-ext`, `aks-<env>-ext-*`) | FI | `extfi`, `extfispot` | `extfiz1`–`z3` | `kv-<env>-ext-fi` | `snet-ext-fi-*` |
| `ext-se` | external (`sub-aks-<env>-ext`, `aks-<env>-ext-*`) | SE | `extse`, `extsespot` | `extsez1`–`z3` | `kv-<env>-ext-se` | `snet-ext-se-*` |

Adding a country adds two zones (`int-xx` to the internal clusters, `ext-xx` to the external ones) following the same pattern, online ([adding a country](3.1-cluster-types-stateless-and-stateful.md#adding-a-country-online)).

Next to the zone vaults, every environment has exactly **one shared platform Key Vault per exposure**:

| Key Vault | Exists | Holds | Access |
|---|---|---|---|
| `kv-<env>-<zone>` | Once per zone and environment, in the zone's exposure subscription | Application secrets (`<app>-<secret>`) of that zone | Read only by the zone's External Secrets Operator, with RBAC + ABAC per application reader identity ([section 2.5](2.5-workload-identity-and-secrets.md)) |
| `kv-<env>-<exposure>-platform` | Once per environment and exposure (`kv-dev-int-platform`, `kv-dev-ext-platform`, …) | The TLS certificates of the exposure's zones (`cert-<zone>-…`), the renewal job's ACME account key and the customer-managed keys of the exposure's clusters (`key-<cluster>-kms`, `key-<cluster>-disk`, `key-sf-pv-<zone>`) | Plain Azure RBAC, role assignments scoped to single certificates and keys ([section 4.1](4.1-encryption-in-transit-and-tls.md#certificates-issued-centrally-distributed-through-the-platform-key-vault), [section 4.2](4.2-encryption-at-rest-and-customer-managed-keys.md)) |

Where another section says `kv-<env>-platform`, it means the platform vault of the exposure in question.

## Cells and bulkheads

The design uses two isolation patterns at two levels, and this document uses their names:

| Term | In this design | Pattern | Limits the impact of |
|---|---|---|---|
| **Exposure** | Internal or external: a subscription per environment with its own cells, stateful cluster, VNets, vaults, ACR and policies ([D52](7.2-decisions.md#decision-matrix)) | Hard boundary (subscription and cluster) | A compromise of an Internet-facing cluster or subscription: it cannot reach the internal workloads' control plane, nodes, identities or secrets |
| **Cell** | One stateless cluster of an exposure (`aks-<env>-<exposure>-sl-az<N>`) with its own VNet, all of it in one availability zone: an external cell runs every external application, an internal cell the internal applications whose home it is | [Cell-based architecture](https://docs.aws.amazon.com/solutions/cell-based-architecture-for-amazon-eks/) | An availability zone outage, a cluster failure, a bad release or a bad cluster upgrade: changes reach one cell at a time |
| **Cell router** | External zones: Azure Traffic Manager answers each client's DNS query with one cell, by the client's network (active-active). Internal zones: the hub Private DNS, kept by ExternalDNS, points each application's name to its home cell ([incoming traffic](3.1-cluster-types-stateless-and-stateful.md#incoming-traffic-from-outside-and-from-inside)) | Cell-based architecture | – (zone-redundant, outside the cells) |
| **Isolation zone** | One exposure × country (`int-fi`, `ext-se`, …) with its own address space, subnets, nodes, Key Vault and policies, present in every cell of its exposure | [Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead) | A noisy, failing or compromised workload of one zone: it cannot use another zone's nodes, network or secrets |
| **Shared tier** | The hubs (one per exposure with its own Firewall, [D53](7.2-decisions.md#decision-matrix); gateways, DNS), Azure PaaS, ACR, Key Vaults, the optional stateful cluster | – | Not split into cells; zone-redundant instead, and changed with extra care |

Two differences from the classic cell-based architecture:

- **Every cell serves every external user.** For external zones the cells are full replicas, aligned with
  availability zones (as in the AWS guidance for EKS, one cluster per availability zone); users are not partitioned
  between cells by tenant or customer. The cell router only pins an external user's *session* to a cell ([DNS affinity](3.1-cluster-types-stateless-and-stateful.md#external-zones-active-active-with-dns-affinity));
  internal applications run in one home cell each and are moved between cells by a migration workflow ([internal zones](3.1-cluster-types-stateless-and-stateful.md#internal-zones-one-home-cell-per-application-moved-by-migration)).
  Partitioning by country would be possible later, because the isolation zones already are the natural partition key.
- **The data is shared.** All cells use the same PaaS services and stateful cluster, so a cell isolates compute and
  releases, not data. Data changes therefore follow the [compatibility rule](3.4-zero-downtime-application-upgrades.md).

In this document "zone" means an isolation zone, unless it says availability zone (AZ) or zone-redundant.
The canonical names are: a cell is `sl-az<N>` in prose and `aks-<env>-<exposure>-sl-az<N>` where the cluster
resource is meant (`aks-<env>-sl-az<N>` where the exposure does not matter); the stateful cluster is `sf` /
`aks-<env>-<exposure>-sf`; exposures are `int` and `ext`; zones are `int-fi`, `ext-se`, and so on.

**If cells ever had to be partitioned by country.** Today every cell holds every isolation zone of its exposure, and a cell is an
availability zone. Should a country need its own blast radius for releases and upgrades as well, the zones are
already the partition key: a country gets its own set of cells per exposure (`aks-<env>-ext-fi-az1`, …) holding only its zone,
with its own Traffic Manager profiles, Private DNS zones and fleet tags. The address plan does not change (the
country's `/16` already summarises its zones), nor do the applications, their manifests or the policies; what
changes is the cluster IaC loop and the release train, which then runs per country. Nothing in the design has to be
undone for that, which is why it is not built now ([decision D01](7.2-decisions.md#decision-matrix)).
