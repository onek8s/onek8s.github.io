# 5.2 Egress control options and the company firewall

Who decides what an application may reach outside the landing zone - the hub Firewall, Cilium inside the cluster, or
both. Every cell runs Azure CNI Pod Subnet with the Cilium dataplane, so every pod keeps its own VNet address up to the
Firewall ([D74](7.2-decisions.md#decision-matrix), [section 2.1](2.1-network-layout.md)); what is left to choose per
cell is whether Advanced Container Networking Services (ACNS) adds Cilium's per-application FQDN policies. This page
compares the two, states the default - **the hub Firewall, without ACNS** ([D61](7.2-decisions.md#decision-matrix)) -
and explains how the platform works with a company-wide firewall that another team owns.
[Section 5.1](5.1-advanced-networking-and-fqdn-egress.md) describes the Cilium FQDN model for the cells that turn ACNS
on; which zones need it is the sign-off [H15](7.2-decisions.md#human-sign-offs-still-needed).

## Who decides egress

The Firewall sees a zone's application pods by their **own addresses**, in the zone's pod subnet, and the platform's
own components (gateways, ESO, Flux, external-dns) by the system subnets. Its rules name subnets or IP groups, so it
opens a destination to a zone, not to one application - but its log names the pod, so every flow can be attributed.

| | Cilium FQDN policies (ACNS) | Hub Firewall (Azure Firewall Premium per exposure, [D53](7.2-decisions.md#decision-matrix)) |
|---|---|---|
| Pros | Per application: a policy selects the application's pods, so two applications in one zone get different destinations. Enforced at the source node - a denied flow never leaves the node. Owned by the team in its own repository (GitOps), changed with the application, checked by the `fqdn-egress` policy against the zone's allow-list. No central bottleneck: the rule set is spread over the clusters | One enforcement point for every flow that leaves the landing zone, from any compute (AKS, VMs, PaaS with VNet integration). Premium features on every flow: IDPS, threat intelligence, TLS inspection and URL filtering, FQDN tags. One log for security, in Log Analytics, naming the pod. Rules are managed and reviewed centrally; applications write no egress policy, and the egress agent proposes the rules from what applications actually do. Survives a misconfigured or compromised cluster: nothing inside the cluster can change it |
| Cons | Needs ACNS (billed per node and hour) and Cilium's DNS proxy - only names the pod resolved are allowed, and DNS rules must cover every search suffix. FQDN and port only: no IDPS, threat intelligence or TLS inspection. Its denials are seen through Hubble, where a cell runs it (D56). Every team must write and keep a policy; a mistake shows up as a broken application. A cluster administrator can change the policies | Opens a destination to a whole zone, not to one application. Cost: a Firewall Premium per exposure (~1.75 USD an hour list) plus data processing per GB. One more hop, and a throughput and availability dependency for every flow. Changes go through central review, so a new dependency waits for a merge. Without TLS inspection its application rules see only the TLS server name |

### ACNS and eBPF host routing in detail

[Advanced Container Networking Services](https://learn.microsoft.com/en-us/azure/aks/advanced-container-networking-services-overview)
(ACNS) is one add-on with three parts, billed per node and hour, on top of Azure CNI powered by Cilium - which the
cells run anyway and which gives Cilium's layer 3 and 4 network policies for free. The cost question is not "Cilium
or not" but "which of ACNS's parts are worth a per-node fee in a cell", and the answer differs per part:

| Part | What it gives | Without it | Enable later |
|---|---|---|---|
| **FQDN filtering** (container network security) | DNS-aware egress: `toFQDNs` rules per application, a DNS proxy that keeps resolving while the Cilium agent restarts, L7 (HTTP, Kafka) rules | Cilium decides by IP and port only; egress out of the cluster is decided by the hub Firewall per zone (the default cell) | **In place**: an ACNS update on a running cell; the applications' `egress` policies then need writing - the egress agent generates them from the per-application rule files, which already hold the destinations per application ([section 5.3](5.3-traffic-flow-documentation.md)) |
| **Container network observability** (Hubble) | Flow logs with verdicts, DNS and HTTP metrics, a UI; dropped flows per namespace in Grafana | Drops are read from Cilium's own counters (`cilium_drops`) and the Firewall's log; no per-flow history inside the cluster | **In place**; off where no pipeline reads the flows ([D56](7.2-decisions.md#decision-matrix)) |
| **eBPF host routing** (container network performance, `BpfVeth`) | Pod traffic bypasses the node's iptables: lower latency, higher throughput, less CPU per node; requires Kubernetes 1.33+, Azure Linux 3.0 or Ubuntu 24.04 on every node, no host iptables rules | The default iptables path; the difference matters at high packet rates and many nodes, not in a small cell | **Only at cluster creation**: a cell is rebuilt behind the cell router with it on (cells are cattle, [section 3.5](3.5-zero-downtime-cluster-upgrades.md#stateless-clusters)) |

What eBPF host routing rules out while it is on - Static Egress Gateway, Confidential VMs, Pod Sandboxing, Windows
nodes, a self-managed Istio ambient - is a second reason to keep it off by default: each of those is an option a
future workload may ask for ([section 7.4](7.4-outlook-2030-and-the-options-kept-open.md)), and turning host
routing off again means another rebuild. With ACNS off the cell keeps its Cilium dataplane and all layer 3/4
policies, its zone baseline and its platform namespace policies; what changes is who decides egress out of the
cluster.

**Where the money goes.** ACNS is priced per node-hour, so its cost scales with the zone nodes that the autoscaler
creates on load - exactly the part of the bill that is supposed to be variable. A hub Firewall Premium
is paid once per exposure whether the cells use it or not ([D53](7.2-decisions.md#decision-matrix)), and it is
already the enforcement point for everything that is not a pod (nodes, platform components, PaaS). Letting it
decide egress for the pods too adds data processing per GB but no fixed cost; adding ACNS adds a fee to every node
of every cell. That is why the default cell runs without ACNS, and FQDN filtering is a per-cell choice for the zones
that need it.

**Portability.** ACNS is an Azure product; the policies it enforces are `CiliumNetworkPolicy` objects that
open-source Cilium enforces on EKS, and GKE's Dataplane V2 has an FQDN policy of its own
([section 1.3](1.3-open-standards-and-portability.md#what-stays-cloud-specific)). The hub Firewall model is the
more portable of the two: every cloud has a central egress firewall with FQDN rules, and the per-application rule
files are plain data.

**The rule.** Start every cell without ACNS. Turn FQDN filtering on, per cell, when a zone needs per-application
egress; turn Hubble on when flow logs are wanted in Grafana; rebuild a cell with eBPF host routing when a measured
CPU or latency problem in the datapath justifies the loss of the features it excludes. Each is a reversible, per-cell
change, and none of them changes an application's manifests.

## The default: the hub Firewall, Cilium inside the cluster

The Firewall decides, with every pod visible to it. Every pod keeps its own address up to the hub Firewall (the
platform configures AKS's ip-masq-agent to translate nothing). No ACNS FQDN policy, no egress
policy in the application repositories:

- **Cilium decides only inside the cluster**, at layers 3 and 4: the zone baseline, namespace isolation and the
  platform namespaces' policies stay; without FQDN filtering there are no DNS-aware rules, so the baseline's DNS rule
  is plain port 53 to kube-dns, and a platform policy per zone (`<zone>-firewall-egress`, Flux Kustomization
  `firewall-egress-<zone>`) lets the zone's application namespaces out to the world. The `fqdn-egress` policy
  ([section 2.7](2.7-policy-enforcement.md)) stays as it is - it only constrains what a team may write.
- **The isolation zone is the egress boundary.** The Firewall decides everything that leaves the cluster from rules
  per application (one rule file per application namespace: the owner, the reason, the review) whose source is the
  zone's IP group (its node and pod subnets in every cell): an allowed
  destination is open to every application of the zone, the rule is removed with the application that asked for it,
  and the Firewall's log names the pod.
- **An AI egress agent proposes the rules** ([section 6.1](6.1-ai-driven-day-2-operations.md)): it reads the flows the
  Firewall denied (Log Analytics), finds the pod behind each source address, checks the destination against the
  application's configuration, and opens one pull request per application with the evidence. Humans of the platform
  and security merge it; nothing is allowed automatically.
- **Nothing in 100.64.0.0/10 leaves the landing zone**: the Firewall Policies' SNAT private ranges are the landing
  zone's own (the RFC 1918 ranges and 100.64.0.0/10), so every allowed flow to the Internet or the corporate network
  is translated to the Firewall's address.

**Making the shared destinations visible.** The Firewall opens a destination to the whole zone - but the
per-application rule files say which application asked for it, why, and the evidence. [Section 5.3](5.3-traffic-flow-documentation.md)
generates from them, and from the applications' own configuration, a picture per application and a picture per zone
(the union the Firewall opens, and who brought each name in) - the review a zone-wide rule needs.

**When to choose Cilium FQDN policies.** An application that must not share its destinations with the rest of its
zone - a regulated integration, a third-party API key that should only ever leave from one place - gets its **own
zone**, or its zone runs on a cell with ACNS FQDN filtering ([section 5.1](5.1-advanced-networking-and-fqdn-egress.md)):
Cilium decides per application, the Firewall stays behind it per zone. ACNS is a per-cluster setting, so the choice
is per cell.

## Working with a company-wide firewall

In many companies the network or security team owns the firewalls, and the platform team does not. The platform's
egress rules are then **requests to that team**, and the design keeps them in a form that team can take without
learning Kubernetes: every rule is a file per application namespace (the zone, a contact, and per destination the
FQDN, protocol, port, reason and evidence) plus the source **IP groups** the platform maintains (one per zone and one
for the exposure's system subnets). Nothing in a rule refers to pods or namespaces, and the egress agent's pull
requests and every human change go through the same review, so the firewall team sees one stream of small, explained
requests with their evidence (the denied flows). How the rules reach the firewall depends on what the company runs
and how much it delegates; the choice is part of the sign-off [H15](7.2-decisions.md#human-sign-offs-still-needed).
From least to most delegation:

| Option | How | Fits |
|---|---|---|
| **1. Pull requests to the firewall team's repository** (no delegation) | The firewall team keeps its policy as code; the platform's rule files live there, or are copied there by a pipeline, and its CODEOWNERS make the firewall team the only approvers. The platform holds no right on the firewall | Any firewall product, because the files are plain data and only the renderer is product-specific; the slowest path, a new dependency waits for the firewall team's review |
| **2. A child Firewall Policy for the platform, the company's policy as its parent** (the design's default, [D53](7.2-decisions.md#decision-matrix)) | Azure Firewall Policies are hierarchical, Microsoft's documented way to delegate ([rule hierarchy](https://learn.microsoft.com/en-us/azure/firewall-manager/rule-hierarchy), [policy overview](https://learn.microsoft.com/en-us/azure/firewall-manager/policy-overview)): the parent's rule collections always win over a child's and threat intelligence can only be made stricter in a child, so nothing the platform writes can override the company's rules. The platform's deployment identity holds a custom role on the child policy alone (Microsoft's "rule collection group author" example, plus `.../ruleCollectionGroups/delete`) and applies the rule files with IaC; its IP groups live in its own resource group | An Azure Firewall takes one policy, so the firewall's assigned policy is the platform's child - which the hub and Firewall per exposure give. The security team owns the parent and the firewall resource (association, SKU, IDPS settings) |
| **3. A rule collection group in the company's own policy** | With one shared Azure Firewall for everything, the platform's rules are rule collection groups inside the company's policy. Microsoft documents the author role on a whole policy, which would let the platform write every group; whether a role assignment scoped to a single rule collection group is honoured is undocumented (V23, [capability matrix](7.2-decisions.md#azure-capability-and-verification-matrix)) | Until V23 is verified, this case falls back to option 1 |
| **4. IP group objects in the company's rules** | The firewall team owns an application rule per destination list (HTTPS 443, its FQDNs); its source is an IP group in the platform's resource group, so the platform puts a zone's prefixes into the group of each list the zone needs with write on its own IP groups only ([IP groups](https://learn.microsoft.com/en-us/azure/firewall/ip-groups)). The firewall team still decides every destination; a new cell or zone needs no change on their side. Delegating *destinations* through an IP group is not recommended: there is no FQDN group, so it would delegate addresses, not names, and lose the TLS server name, TLS inspection and web categories. "Everything over HTTPS to `*`" from the platform's groups fits only a cell with Cilium FQDN policies, where Cilium decides per application | The permission the firewall team's deployment needs to reference the platform's groups and how long a change takes to reach the firewall are V24; a check that the groups hold only the platform's prefixes is agreed with the firewall team |

What the platform needs from the firewall team, in any case:

- **Source addresses that stay stable**: the zones' and system subnets' prefixes come from the address plan
  ([section 3.1](3.1-cluster-types-stateless-and-stateful.md#vnets-and-address-plan)) and are published as IP groups, so
  a new cell changes an IP group, not a rule.
- **The platform's base rules** (AKS's required FQDNs, Entra ID, Azure Monitor, the GitOps sources) in the parent or a
  group of their own, reviewed once.
- **Read access to the firewall's denied flows** (its diagnostic setting into a Log Analytics workspace the platform
  can query, through the hub's Azure Monitor Private Link scope): the egress agent's only input.
- **Translation at the firewall** for everything leaving the landing zone's own ranges (SNAT private ranges), so
  the cells' 100.64 pod addresses never leave it.

## Cost

Per stateless cell:

| | Default cell (no ACNS) | Cell with Cilium FQDN policies |
|---|---|---|
| Control plane | Standard tier, 0.10 USD an hour per cell (list) | same |
| System pool VMs | two D4 per cell | same |
| ACNS | none | every node, every hour |
| Hub Firewall | shared per exposure ([D53](7.2-decisions.md#decision-matrix)) | same |
| Firewall data processing | every flow leaving the cluster | only what Cilium let out |
| Address space | nodes in `/24` slots and a `/16` of 100.64.0.0/10 for pods | same |
| Firewall log ingestion | denials (all flows only while learning a default-allow environment) | same |

ACNS and Azure Firewall are priced in the Azure pricing calculator (per node and hour for ACNS; per deployment hour and
per GB processed for the Firewall); the list prices are not repeated here because they change.
