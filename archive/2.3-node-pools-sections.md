## GPUs, chosen by the application (from 2.3 Node pools)

An application that needs a GPU asks for it the same way ([decision D42](../design/7.2-decisions.md#decision-matrix)): it requests
the GPUs (`resources.limits: nvidia.com/gpu: 1`) and carries the label `platform/accelerator: nvidia-gpu`. An Azure
Policy mutation turns the label into the toleration of the zone's GPU pool; the request is what makes the autoscaler
grow it.

- **One GPU pool per zone**, `<zone>gpu`, in the zone's subnets: on-demand only, amd64, from zero, the zone's label
  and taint plus `platform/accelerator=nvidia-gpu:NoSchedule`. No other pool offers a GPU, and no pod without the
  label tolerates these nodes, so ordinary pods never land on them.
- **Only VM sizes with VNet encryption and encryption at host**, like every zone node. Among the GPU sizes that is
  today only NC H100 v5 (`NC40ads_H100_v5` with one H100, `NC80adis_H100_v5` with two).
- **AKS's managed GPU stack** (preview): AKS installs and patches the NVIDIA driver, the device plugin and the DCGM
  metrics exporter on the nodes, so the platform runs no GPU operator.
- **Cost**: a GPU node is the most expensive thing in a cell. The pool scales to zero and the autoscaler removes an
  empty node after its scale-down delay, its maximum is set per cluster, and the family's vCPU quota is raised only
  where GPUs are wanted. OpenCost reports the node's cost against the namespace that used it
  ([section 2.6](../design/2.6-application-multi-tenancy.md#ownership-and-cost)).
- **Validation**: Azure Policy rejects a GPU request without the label, the label without a GPU request (a pod that
  would hold a GPU node without using its GPU), a GPU pod that is not amd64, and the GPU toleration without the label.
  The stateful cluster offers no GPUs.
