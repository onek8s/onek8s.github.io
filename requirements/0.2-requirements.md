# 0.2 Requirements

The requirements of the platform, owned by humans ([how we work](../README.md#how-we-work-requirements-driven-collaboration)): a change to a requirement needs
a human's approval. The acceptance column names the [acceptance criteria](0.3-acceptance-criteria.md) that prove each
requirement; the requirement and isolation tests are tagged with the requirement number they cover. How the design
meets each requirement is design [section 1.2](../design/1.2-how-the-design-meets-the-requirements.md).

| # | Requirement | Acceptance |
|---|---|---|
| <a id="r1"></a>R1 | Internal and external workloads isolated – at subscription and cluster level (security, 2026-10-14) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): one exposure per cluster and subscription |
| <a id="r2"></a>R2 | Workloads of different countries isolated – node pool and network are enough | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every flow between zones blocked |
| <a id="r3"></a>R3 | Isolation = Key Vault + network + node pool per type | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): another zone's pods, nodes and Key Vault blocked; every zone complete |
| <a id="r4"></a>R4 | Only connectivity mandatory for Kubernetes allowed between zones | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every flow between zones blocked and logged by the Firewall |
| <a id="r5"></a>R5 | Countries can be added online | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every zone complete; adding a country in [upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| <a id="r6"></a>R6 | Azure CNI powered by Cilium in every cluster | Design review |
| <a id="r7"></a>R7 | Control plane in a dedicated network | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the API server only from the management VNet; local admin and SSH refused |
| <a id="r8"></a>R8 | Cost-optimised compute: applications choose amd64 or arm64 and on-demand or spot nodes, the platform supports all of them | [Performance](0.3-acceptance-criteria.md#performance-and-capacity): scale-out with arm64 and spot, spot eviction |
| <a id="r9"></a>R9 | Workload identities wherever possible, secrets only when needed | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): no local auth found by Resource Graph |
| <a id="r10"></a>R10 | Key Vault multi-tenancy with [Azure RBAC + ABAC](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-abac) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): another application's secret refused by ABAC |
| <a id="r11"></a>R11 | Applications never read Key Vault directly; External Secrets Operator is mandatory for them | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): an application that reads Key Vault itself is refused |
| <a id="r12"></a>R12 | Certificates distributed through Key Vault, shared by all clusters | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the certificate from the vault to the listener; renewal in [upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| <a id="r13"></a>R13 | Applications isolated in namespaces + network policies | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): namespace groups and roles |
| <a id="r14"></a>R14 | Every workload's owner and cost are known | Forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests); cost in [operations](0.3-acceptance-criteria.md#operations) |
| <a id="r15"></a>R15 | One policy engine | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every forbidden manifest denied by admission |
| <a id="r16"></a>R16 | Applications and how they are deployed do not change between clouds (portability of the application contract) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): application repositories scanned for cloud-specific objects |
| <a id="r17"></a>R17 | Two cluster types: stateless and stateful | Design review |
| <a id="r18"></a>R18 | Stateful cluster is the last option | Design review |
| <a id="r19"></a>R19 | Stateful cluster exists at most once per exposure (R1), in the backend network with the Azure PaaS services, **no Internet egress and no public endpoints**; the only outbound destinations outside Private Link are allow-listed Microsoft control-plane endpoints that have no Private Link (Entra ID for workload identity, the Azure Policy add-on) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): no Internet destination from the stateful cluster but the documented exceptions |
| <a id="r20"></a>R20 | Stateful cluster spread over availability zones and running AKS LTS | [High availability](0.3-acceptance-criteria.md#high-availability-and-resilience): AZ outage (stateful cluster, if built) |
| <a id="r21"></a>R21 | Stateful cluster: VNet-integrated CNI, no Gateway API implementation (and no Ingress), applications handle TLS | Design review |
| <a id="r22"></a>R22 | Stateless clusters: pod subnet CNI, no service mesh / mTLS / application TLS, TLS-only Gateway API (no Kubernetes Ingress) | [CIS benchmark](0.3-acceptance-criteria.md#cis-benchmark): TLS on every gateway listener; forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests) |
| <a id="r23"></a>R23 | Stateless: separate cluster per availability zone (at least two), ≥ 2 copies of every application, scaled on load | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the cell's settings; [performance](0.3-acceptance-criteria.md#performance-and-capacity) and [high availability](0.3-acceptance-criteria.md#high-availability-and-resilience) |
| <a id="r24"></a>R24 | Every application has health probes, and every application published through a gateway a health endpoint the platform probes | Forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests); failover in [high availability](0.3-acceptance-criteria.md#high-availability-and-resilience) |
| <a id="r25"></a>R25 | dev, acc and prd environments kept in sync | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every cell in sync with Git and its IaC; [rebuild](0.3-acceptance-criteria.md#rebuild-backup-and-recovery) |
| <a id="r26"></a>R26 | Fully automated zero-downtime upgrades of applications and clusters | [Zero-downtime upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| <a id="r27"></a>R27 | Update policy: stateful cluster only when absolutely necessary, stateless clusters at two speeds | [Zero-downtime upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes): minor and node image upgrades |
| <a id="r28"></a>R28 | Data at rest encrypted with customer-managed keys: own key for each control plane and each node pool, stored in the platform Key Vault | [CIS benchmark](0.3-acceptance-criteria.md#cis-benchmark): KMS; design review |
| <a id="r29"></a>R29 | Traffic exiting the cluster is allowed only to named destinations (FQDNs) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): egress to an unnamed FQDN or an IP address denied |
| <a id="r30"></a>R30 | Day 2 operations driven by AI agents, also in prd, but only through GitOps / IaC pull requests within human-defined guardrails | [Upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes): an agent change through every risk tier and the kill switch |
| <a id="r31"></a>R31 | Observability, including tracing, with Grafana Cloud; anyone allowed to connect to it may see all data | [Operations](0.3-acceptance-criteria.md#operations): telemetry and no secrets in it |
| <a id="r32"></a>R32 | Protect against losing the region with immutable backups in another region; back up only persistent data, not whole clusters | [Rebuild, backup and recovery](0.3-acceptance-criteria.md#rebuild-backup-and-recovery) |
