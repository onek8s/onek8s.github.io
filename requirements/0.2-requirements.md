# 0.2 Requirements

The requirements of the platform, owned by humans ([section 0.1](0.1-how-we-work.md)): a change to a requirement needs
a human's approval. The acceptance column names the [acceptance criteria](0.3-acceptance-criteria.md) that prove each
requirement; the requirement and isolation tests are tagged with the requirement number they cover. How the design
meets each requirement is design [section 1.2](../design/1.2-how-the-design-meets-the-requirements.md), and why, the
[decision log](../design/7.2-decisions.md).

| # | Requirement | Acceptance |
|---|---|---|
| R1 | Control plane in a dedicated network | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the API server only from the management VNet; local admin and SSH refused |
| R2 | Internal and external workloads isolated – at subscription and cluster level (security, 2026-10-14) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): one exposure per cluster and subscription |
| R3 | Workloads of different countries isolated – node pool and network are enough | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every flow between zones blocked |
| R4 | Isolation = Key Vault + network + node pool per type | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): another zone's pods, nodes and Key Vault blocked; every zone complete |
| R5 | Only connectivity mandatory for Kubernetes allowed between zones | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every flow between zones blocked and logged by the Firewall |
| R6 | Applications isolated in namespaces + network policies | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): namespace groups and roles |
| R7 | Key Vault multi-tenancy with [Azure RBAC + ABAC](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-abac) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): another application's secret refused by ABAC |
| R7a | Workload identities wherever possible, secrets only when needed | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): no local auth found by Resource Graph |
| R7b | Applications never read Key Vault directly; External Secrets Operator is mandatory for them | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): an application that reads Key Vault itself is refused |
| R8 | Two cluster types: stateless and stateful | Design review |
| R8a | Stateful cluster is the last option | Design review |
| R9 | Stateful cluster exists at most once per exposure (R2), in the backend network with the Azure PaaS services, **no Internet egress and no public endpoints**; the only outbound destinations outside Private Link are allow-listed Microsoft control-plane endpoints that have no Private Link (Entra ID for workload identity, the Azure Policy add-on) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): no Internet destination from the stateful cluster but the documented exceptions |
| R9a | Stateful cluster: VNet-integrated CNI, no Gateway API implementation (and no Ingress), applications handle TLS | Design review |
| R9b | Stateless clusters: pod subnet CNI, no service mesh / mTLS / application TLS, TLS-only Gateway API (no Kubernetes Ingress) | [CIS benchmark](0.3-acceptance-criteria.md#cis-benchmark): TLS on every gateway listener; forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests) |
| R10 | Stateful cluster spread over availability zones and running AKS LTS | [High availability](0.3-acceptance-criteria.md#high-availability-and-resilience): AZ outage (stateful cluster, if built) |
| R11 | Stateless: separate cluster per availability zone (at least two), ≥ 2 copies of every application, scaled on load | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the cell's settings; [performance](0.3-acceptance-criteria.md#performance-and-capacity) and [high availability](0.3-acceptance-criteria.md#high-availability-and-resilience) |
| R12 | Fully automated zero-downtime upgrades of applications and clusters | [Zero-downtime upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| R12a | Update policy: stateful cluster only when absolutely necessary, stateless clusters at two speeds | [Zero-downtime upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes): minor and node image upgrades |
| R13 | dev, acc and prd environments kept in sync | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every cell in sync with Git and its IaC; [rebuild](0.3-acceptance-criteria.md#rebuild-backup-and-recovery) |
| R14 | One policy engine | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every forbidden manifest denied by admission |
| R15 | Certificates distributed through Key Vault, shared by all clusters | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): the certificate from the vault to the listener; renewal in [upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| R16 | Countries can be added online | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): every zone complete; adding a country in [upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes) |
| R17 | Cost-optimised compute: applications choose amd64 or arm64 and on-demand or spot nodes, the platform supports all of them | [Performance](0.3-acceptance-criteria.md#performance-and-capacity): scale-out with arm64 and spot, spot eviction |
| R18 | Day 2 operations driven by AI agents, also in prd, but only through GitOps / IaC pull requests within human-defined guardrails | [Upgrades and changes](0.3-acceptance-criteria.md#zero-downtime-upgrades-and-changes): an agent change through every risk tier and the kill switch |
| R19 | Azure CNI powered by Cilium in every cluster | Design review |
| R20 | Traffic exiting the cluster is allowed only to named destinations (FQDNs) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): egress to an unnamed FQDN or an IP address denied |
| R21 | Data at rest encrypted with customer-managed keys: own key for each control plane and each node pool, stored in the platform Key Vault | [CIS benchmark](0.3-acceptance-criteria.md#cis-benchmark): KMS; design review |
| R22 | Observability, including tracing, with Grafana Cloud; anyone allowed to connect to it may see all data | [Operations](0.3-acceptance-criteria.md#operations): telemetry and no secrets in it |
| R23 | Protect against losing the region with immutable backups in another region; back up only persistent data, not whole clusters | [Rebuild, backup and recovery](0.3-acceptance-criteria.md#rebuild-backup-and-recovery) |
| R24 | Every application has health probes, and every application published through a gateway a health endpoint the platform probes | Forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests); failover in [high availability](0.3-acceptance-criteria.md#high-availability-and-resilience) |
| R25 | Every workload's owner and cost are known | Forbidden manifests in the [isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests); cost in [operations](0.3-acceptance-criteria.md#operations) |
| R26 | Applications and how they are deployed do not change between clouds (portability of the application contract) | [Isolation tests](0.3-acceptance-criteria.md#requirement-and-isolation-tests): application repositories scanned for cloud-specific objects |
