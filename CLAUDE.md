# OneK8s design - notes for Claude sessions

The shared working notes for all OneK8s repos (what is deployed, decisions, gotchas) are in
`onek8s/aks-terraform/CLAUDE.md`. Read that first.

This repo is the design, published with GitHub Pages (`docs/<part>.<page>-*.md`: `1.2-requirements.md`,
`7.2-decisions.md` (decision log, capability matrix, human sign-offs), `7.3-open-questions.md` (only what still needs a
human); diagrams in `diagrams/`, rendered as described in `docs/8.2-editing-the-pictures.md`; the site's reading order is
`_data/nav.yml`, repeated with a description per page in `README.md`'s Contents - a new page goes into both). A decision goes into
`7.2-decisions.md` with its options and justification; `scripts/check.sh` runs in CI (diagram freshness, links).
When an implementation decision changes the design, update the affected sections here in the same
round. Decisions already reflected: Traffic Manager instead of Front Door; public API server as a dev
lab exception (until D58); zone gateways and ESOs on the system pool so zone nodes scale to zero; spot and
architecture chosen per application with on-demand fallback; App Routing's Gateway API (`approuting-istio`)
instead of Traefik; GPU NodePools per zone on request (D42); cost per team from OpenCost in Grafana's k8s-monitoring
instead of the AKS cost analysis add-on (D46); namespace ownership labels (D47, R25); namespace access by Entra ID groups bound to `view`/`edit`/`admin`, with the matching Key Vault rights on the namespace's secrets (D49); soft multi-tenancy - tenants list no namespaces or secrets, platform viewers list both through a resource-group custom role, same pattern for other PaaS (D50); `edit` writes secrets without reading them (custom Key Vault Secrets Editor role), `admin` keeps Secrets Officer (D51); a hub VNet and Azure Firewall Premium per exposure with no route between them, the management VNet peered to both (D53); IPv4 only, no IPv6 planned (D54); V13 re-opened because the network isolated cluster docs list only the `NodeImage` and `None` OS channels. The Gateway API implementation is a per-cluster flag - App Routing in acc/prd, Traefik in the dev lab because istiod's requests cannot be tuned (Azure/AKS#5939), and the dev cells without the VPA add-on on one 8 GiB system node (D55); the dev cells keep ACNS for FQDN policies and eBPF host routing but turn Hubble off (D56). The dev lab's API servers are private too (D58, Private Link - Azure refuses VNet integration on encrypted networks with v4+ sizes, open as H14 - public FQDN to the private address, runners on labfw's VPN). The dev lab (D57, 2026-10-15) is the internal exposure, Finland only (`int-fi`; Sweden disabled by `isolation_zones.<zone>.enabled = false`), one cell in AZ1 in germanywestcentral, routed through labfw in the hub in `firewall`-mode topology (no platform gateway, no Flux webhook, no Traffic Manager). A second dev cell, az3 (D59, Sweden's `int-se`), has no overlay - D59 is NOT decided: both egress models (Cilium FQDN policies in az2, the hub firewall in az3) are configuration options under test because their feature sets differ (H15): pods in 100.64.0.0/16 keep their addresses to the hub firewall, which decides egress from per-application rules that an AI egress agent proposes from the denied flows; SNAT for everything leaving the landing zone's ranges. No public endpoints (D60, 2026-10-15): vaults, registry, Foundry, Terraform state, Log Analytics (hub Azure Monitor Private Link scope) take no public network access; runners on labfw's VPN; KMS data encryption (preview) reaches the private vault as a trusted service; exceptions are AKS-managed node resources and the ALZ bootstrap state. Proposed default egress model (D61, section 5.2, 2026-10-16): overlay + hub Firewall only, without ACNS (cost); per-application granularity via ACNS or node subnet per cell; a company-owned firewall through a child Firewall Policy under its parent (custom RCG-author role on the child) or pull requests to the firewall team. Container registry tier per environment (D62, 2026-10-16): Premium with a private endpoint in prd only; Basic on its public endpoint (Entra ID only) in dev and acc - aks-terraform `shared/` `container_registry_sku` defaults from the environment. Traffic flow documentation generated from Git (D63, section 5.3, 2026-10-17): a Mermaid page per application and per zone from the per-application firewall rule files + the application's Flux configuration + the zone allow-lists + the cell tfvars, each destination with a status (allowed/named, allowed/unexplained, named/denied, proposed, zone); `aks-agent docs traffic` in aks-ai-agents generates, the documentation agent opens the PR; the pages live in azure-landing-zone `docs/traffic-flows/<spoke>/` (aks-terraform workflow `Traffic flow docs`, by hand). Optional features are added only by the rule of D64 (section 7.4: what holds, what changes by 2030, the options kept open with trigger, path and cost); section 5.2 has the ACNS/eBPF host routing deep dive and section 4.1 the service-mesh-or-not reasoning.
